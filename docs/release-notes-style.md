# リリース告知（X）の書き方

このサイトの更新をXで告知するときの型と言葉づかいをまとめる。
毎回ゼロから考えず、ここの手順どおりに書けば同じトーンになるようにする。

対象: `sangasanga.stars.ne.jp` の更新告知全般（日程ページ、予想スカッド作成など）

---

## 1. 読み手

**京都サンガのサポーター。エンジニアではない。**

- 「不具合が直った」より「**自分に何が良くなるか**」に関心がある
- スマホで、タイムラインを流し読みしている
- 技術的な仕組みには興味がない。専門用語が出た時点で読むのをやめる

---

## 2. 3つの原則

### 原則1: 効果を先に、手段を後に

いちばん伝えたいのは「利用者から見て何が変わったか」。
実装上どこをどう変えたかは、必要なら理由として後ろに添える。

| | 例 |
|---|---|
| ✅ 良い | 選手カードが大きく、重ならずに表示されるようになりました |
| ❌ 惜しい | 控えメンバーの登録欄を作りました |

後者は「作った側の視点」。読み手には、それで何が良くなるのか分からない。

### 原則2: 症状の言葉で書く

不具合は、原因ではなく**利用者が見ていた現象**で書く。

| 内部の言葉 | 告知での言い方 |
|---|---|
| スクロールチェーン | 選手を選ぶ画面でスクロールすると、後ろの画面が動いてしまう |
| `filter: drop-shadow` の描画不具合 | iPhoneで画像を作ると影が崩れる |
| カードの重なり判定 | 選手カードが重なる |
| LocalStorage | 保存したデータ |
| フォーメーションのスロット座標 | 選手の並び |

### 原則3: 1投稿に主役は1つ

修正が5件あっても、主役は1件。残りは1行にまとめるか、書かない。
全部を同じ重さで並べると、何も伝わらない。

---

## 3. 構成の型

```
1行目  何のツール／ページを更新したか（+ ⚽）
空行
2文目  いちばんの変更（＝効果）
空行
3文目  その理由・補足（手段はここ）
空行
URL
```

例（2026-08-20 予想スカッド作成ツール）:

```
予想スタメン作成ツールを更新しました⚽

いちばんの変更は、選手カードが大きく、重ならずに表示されるようになったこと。

控えメンバーの登録を編集画面側へ移し、そのぶんピッチを広くとりました。控えは何人でも登録できます。

https://sangasanga.stars.ne.jp/squad.html
```

小さな修正だけのときは、箇条書きにしてもよい。その場合も**先頭が効果**であること。

---

## 4. 言葉づかい

### 使う

- です・ます調
- 「〜できるようになりました」「〜を直しました」
- 絵文字は⚽を1個だけ、1行目の末尾に

### 使わない

- 専門用語（CSS、JavaScript、キャッシュ、レンダリング、バグ、リリース、デプロイ、コミット…）
- 誇張（大幅に、劇的に、圧倒的に、神アップデート）
- 謝りすぎ（ご迷惑をおかけしました、大変申し訳ございません）
  - 不具合修正は淡々と書く。深刻な事故のときだけ一言添える
- 絵文字の多用、記号の装飾（★、■、▼ の連打）
- ハッシュタグの盛りすぎ。付けるなら1〜2個まで

## 5. 文字数

Xは日本語だと**実質140文字**（全角1文字=2、URL=23で固定、上限280）。

目安は **240〜260**。埋めきらないほうが読みやすい。

数える方法（このリポジトリの `docs/` から実行）:

```bash
python3 - <<'PY'
import unicodedata, re
t = """（ここに本文）"""
t = re.sub(r'https?://\S+', 'U'*23, t)
print(sum(2 if unicodedata.east_asian_width(c) in 'WF' else 1 for c in t), '/ 280')
PY
```

## 6. 画像

**見た目が変わる更新には必ず付ける。** タイムラインでは画像のほうが先に目に入る。

| 更新の種類 | 付ける画像 |
|---|---|
| 表示や生成物が良くなった | **修正前 → 修正後の2枚**（この順で添付） |
| 機能が増えた | その機能を使っている画面 |
| データ更新のみ | なくてよい |

前後比較を撮るときは、**変わった点以外をすべて揃える**。
選手・フォーメーション・控えの人数・スタイルが違うと、どこが変わったのか読み取れない。

### 代替テキスト（alt）

画像には必ず入れる。見えない人にも同じ情報が届くようにする。

- 何の画面か
- 画像で見てほしい違いは何か

例:

> 予想スタメンの生成画像。修正前は選手カードが重なり、下部の控え欄が3行を占めている。

## 7. 投稿前チェック

- [ ] 1行目を読んだだけで、何が良くなったか分かるか
- [ ] 専門用語が残っていないか（§4の「使わない」を確認）
- [ ] 主役が1つに絞れているか
- [ ] 文字数は260以内か
- [ ] URLは正しいか（本番は `sangasanga.stars.ne.jp`。GitHub PagesのURLを貼らない）
- [ ] 本番へのデプロイは**済んでいるか**（告知が先に出ると、見に行った人が古い画面を見る）
- [ ] 画像の代替テキストを入れたか
- [ ] 非公式ファンサイトとして、公式の発表と誤解される書き方になっていないか

---

## 8. 作成を依頼するときのメモ

AIに作らせる場合は、次を伝えると早い。

- 今回の**主役**（いちばん伝えたい効果）
- 添える修正の一覧
- 画像を付けるかどうか
- 複数案が欲しいか

案は2〜3案もらって選ぶとよい。文字数はこのドキュメントの§5に従って測ってもらう。
