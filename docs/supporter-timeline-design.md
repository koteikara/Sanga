## この文書の目的

京都サンガF.C.の公式情報に散在する「チケット販売」「応募締切」「試合日イベント」「開門」「キックオフ」などを、
サポーター本人の時間軸に統合する非公式ツール `SANGA SUPPORTER TIMELINE` の企画設計を記録します。

現時点では企画・設計の記録のみで、実装、依存追加、公開HTML/CSS/JavaScript変更、公開JSON変更は行っていません。

閲覧用の元資料（HTML）は `docs/concept/supporter-timeline-design.html` です。内容の正本は本文書とします。

## 位置づけ

本企画は、`docs/service-scope.md` で「ニュース連動カレンダー」として構想していたサービスの後継です。
対象とする情報（チケット販売開始、ファンクラブグレード別販売開始、イベント申込開始・終了、グッズ販売、キャンペーン締切）は同じですが、
主表現をカレンダーではなく時系列タイムラインに変え、Google Calendarを出力先の一つに格下げした点が異なります。

| 観点 | ニュース連動カレンダー（従来構想） | SUPPORTER TIMELINE（本企画） |
| --- | --- | --- |
| 主表現 | 公開カレンダー | 1本のサポータータイムライン |
| 利用者の操作 | 必要な予定を自分のカレンダーへコピー | 画面上で次の行動と当日の流れを確認 |
| Google Calendar | 最終出力先 | 出力先の一つ |
| 個人の予定 | 対象外 | 公式イベントと同じモデルで同じ時系列に並べる |
| 日時抽出 | 公式ニュースから抽出＋人間確認 | 同じ（構造化ページを先、ニュースを後） |

役割分担の考え方（年間スケジュールページは試合予定・パーソナライズ・SNS共有に集中し、ニュース由来の日時は別サービスで扱う）は
`docs/service-scope.md` のまま引き継ぎます。名称と主表現の変更は本文書を正とし、`docs/service-scope.md` からも参照します。

## 解決したい課題

公式情報が「時系列」でつながっていません。

- チケット販売開始が別ページ・別記事にある。
- イベント開始時刻が試合ニュースの本文に埋もれる。
- 応募締切・引換開始・グッズ販売なども別管理になっている。
- 試合当日の「どの順で動くか」は利用者が自分で組み立てる必要がある。
- 結果として「販売開始を忘れた」「イベントが重なった」「座席に戻る時間が足りない」が起きる。

## 設計原則

主役は「試合」ではなく「サポーター本人」です。すべての情報を、試合単位ではなく1本のサポータータイムラインに並べます。

- 表示の絞り込み軸: ALL / チケット / 応募 / 試合当日 / MY予定
- 各イベントに `match_ids` を持たせ、必要なときだけ特定試合へ絞り込む。
- 公式情報と個人の予定を同じモデルで扱い、UI上は同じ時系列に並べる。
- 情報の正本はタイムライン側のデータとし、Google Calendarなど外部は出力先として扱う。
- 誰向けの情報かは、イベント側に事実として持たせ、利用者の属性との照合は端末内で行う。

## 体験イメージ

「次にやること」と「全体タイムライン」を分けます。

- 次にやること（1件）: 例）明日 12:00 / 🎫 柏戦 SC最速先行販売 / あと13時間
- 全体タイムライン（時系列）: 例）
  - 8/27 12:00 🎫 柏戦 SC最速先行販売開始（公式 / ACTION）
  - 8/29 16:30 🎪 水戸戦 ○○イベント受付開始（公式 / INFORMATION）
  - 8/30 17:10 👤 ○○ブースへ（MY予定）
  - 8/30 19:00 ⚽ 水戸戦 KICK OFF（公式 / MATCH）

## 情報モデル

`TimelineEvent` を最小単位にします。キー名は既存の公開JSON（`public/data/matches.json`）に合わせてスネークケースを使います。

```json
{
  "id": "ticket-sec03-sc",
  "starts_at": "2026-08-30T12:00:00+09:00",
  "ends_at": "",
  "type": "ticket",
  "title": "SC最速先行販売開始",
  "source": "official",
  "action_type": "action",
  "match_ids": ["sec03"],
  "source_url": "https://...",
  "source_checked_at": "2026-08-26",
  "status": "confirmed",
  "is_visible": true
}
```

| キー | 値 | 補足 |
| --- | --- | --- |
| `id` | イベント固有ID | `種別-試合ID-識別子` を基本にし、重複排除・変更検知の同一性キーにする |
| `starts_at` | ISO 8601（`+09:00` 付き） | 日付のみ判明で時刻未定の場合の表現は未確定（後述） |
| `ends_at` | ISO 8601または空文字 | 申込期間・イベント開催時間帯を持つ場合に使う |
| `type` | `ticket` / `entry` / `event` / `goods` / `match` / `personal` | 表示の絞り込み軸に対応させる |
| `source` | `official` / `personal` | 将来 `jleague` などを足せるようにする |
| `action_type` | `action` / `information` / `personal` | 表示カテゴリ（後述） |
| `match_ids` | 試合IDの配列 | 0件・1件・複数件を許可し、クラブ全体イベントにも対応する |
| `status` | `confirmed` / `tentative` | `docs/data-schema.md` の状態語彙に揃える |
| `is_visible` | 真偽値 | `matches.json` と同じく公開制御に使う |

MY予定（利用者自身の予定）も同じモデルで扱います。

```json
{
  "id": "my-seat-sec03",
  "starts_at": "2026-08-30T18:10:00+09:00",
  "type": "personal",
  "title": "座席へ移動",
  "source": "personal",
  "action_type": "personal",
  "match_ids": ["sec03"]
}
```

MY予定は個人状態のためLocalStorage側で扱い、公開JSONには含めません（`AGENTS.md` の保護事項、`docs/personalization.md` に従う）。
LocalStorageキーは既存の命名に合わせ、`sanga-timeline-personal-events-v1` のような `sanga-<機能>-<用途>-v1` 形式を使います。
既存の `sanga-schedule-*` キーは変更しません。

## 既存データとの整合

タイムラインは新規データを持ちますが、試合そのものの正本は既存のまま `public/data/matches.json` です。

- 試合IDは `matches.json` の `id`（現在は `sec01` 〜 `sec38` 形式）をそのまま外部キーとして使います。
  独自のID体系（`2026-j1-kashiwa-home` のような形）は作りません。
  カップ戦・ACL戦への拡張が必要になった場合は、`docs/service-scope.md` と `docs/data-schema.md` が想定する
  `j1-sec01`、`lev-r1` 形式への移行に合わせます。
- タイムライン側の公開データファイル名は、`docs/service-scope.md` の予告に合わせて `public/data/calendar-events.json` を第一候補とします。
  ファイル名を変える場合は `docs/service-scope.md` と `docs/data-schema.md` も同時に更新します。
- 試合の日程が未定・候補日ありの場合（`matches.json` の `date_candidates`、`status: tentative`、`match_status: 未定`）、
  そこにぶら下がるイベントの日時も確定できません。この扱いは未確定事項として後述します。
- 公開データを追加する場合は、既存の検証の作り（`tools/validate-matches.js`、`tools/validate-players.js` など）に倣って
  `tools/validate-calendar-events.js` を用意し、`npm run check:data` から呼びます。検証なしで公開データを増やしません。

## サポータープロフィール

同じ公式情報でも、次に取るべき行動は人によって違います。ファンクラブのグレードが違えば先行販売の開始日時が違い、
居住地が違えばアウェイ戦の位置づけが違い、興味が違えば見たいイベントが違います。
タイムラインを「自分の時間軸」にするには、この属人的な条件を扱う必要があります。

### 何を持つか

`SupporterProfile` を利用者ごとに1件だけ持ちます。すべて任意入力で、未設定でもタイムラインは成立させます。

```json
{
  "fc_grade": "",
  "area": "",
  "home_base": "",
  "interests": [],
  "travel_minutes_to_sanga_stadium": null,
  "updated_at": "2026-08-26"
}
```

| キー | 値 | 何に効くか |
| --- | --- | --- |
| `fc_grade` | ファンクラブ会員種別のコード（非会員を含む） | 自分に該当する先行販売の開始日時だけを「次にやること」に出す |
| `area` | 居住エリアの粗い区分（例: 京都市内 / 京都府内 / 関西 / その他） | HOME中心かAWAY遠征中心かの重み付け、近隣アウェイの判定 |
| `home_base` | 出発地の目安（駅名などの選択肢） | 当日プランでの移動時間の逆算（Phase 4） |
| `interests` | 興味タグの配列（例: `goods` / `event` / `kids` / `away` / `collect`） | イベント種別の並べ替えと絞り込み |
| `travel_minutes_to_sanga_stadium` | 分（整数） | 「家を出る」時刻の逆算の初期値 |

**自由入力の住所、氏名、会員番号、連絡先は持ちません。** 保存するのは選択肢のコードだけです。
居住地も番地レベルではなくエリア区分にとどめ、必要になった時点で粒度を上げるか判断します。

### どこに保存するか

`docs/personalization.md` の方針どおり、LocalStorageに保存し、公開JSONには一切含めません。

- キーは `sanga-timeline-profile-v1`（`sanga-<機能>-<用途>-v1` 形式）。
- 既存の `sanga-schedule-*` キーとは分けます。既存キーは変更しません。
- 保存内容削除ボタンの対象に含め、何が消えるかを画面上で明示します。
- 端末を変えると消えるため、書き出し・読み込み（JSONのコピー＆貼り付け）を早い段階で用意します。

プロフィールはサーバーへ送りません。照合はすべて利用者の端末内で行います。
この方式なら、個人の属性がどこにも記録されないまま、パーソナライズだけが成立します。

### イベント側に持たせる条件

プロフィールと突き合わせるため、`TimelineEvent` に「誰向けか」を持たせます。

```json
{
  "id": "ticket-sec03-fc-diamond",
  "starts_at": "2026-08-27T12:00:00+09:00",
  "type": "ticket",
  "title": "ファンクラブ先行販売開始（ダイヤモンド）",
  "audience": { "fc_grade": ["diamond"] },
  "interest_tags": [],
  "match_ids": ["sec03"]
}
```

| キー | 意味 |
| --- | --- |
| `audience` | このイベントが該当する条件。空または未指定なら全員向け |
| `audience.fc_grade` | 該当する会員種別コードの配列 |
| `interest_tags` | 興味タグ。`interests` と突き合わせて並べ替えに使う |

イベント側が持つのは「事実」（このグレードの販売はこの日時）だけです。「誰に見せるか」の判断は端末内の照合に任せます。
会員種別のコードは公式の名称を確認してから確定します（現時点では仮）。

### 表示の原則

**既定は「隠す」ではなく「並べ替えと強調」です。**

- 自分に該当するイベントを上に出し、バッジで理由を示す（例: 「あなたのグレード」）。
- 該当しないイベントも一覧からは消しません。プロフィールの設定ミスや、家族分の購入など、
  自分の属性と関係なく知りたい場合があるためです。
- 明示的に「自分に関係するものだけ」を選んだときだけ絞り込みます。
- プロフィール未設定でも全イベントが見えます。設定を促す表示は出しますが、必須にしません。
- 強調は色だけに依存せず、ラベルやアイコンと併記します（`AGENTS.md` の実装上の保護事項）。

### 段階

| Phase | 扱う項目 |
| --- | --- |
| Phase 1 | なし（プロフィールなしでタイムラインが成立することを先に確認する） |
| Phase 2 | `fc_grade`。先行販売のグレード別日時を扱えるようになった時点で導入する |
| Phase 3 | `interests`。イベント種別が増えて絞り込みが要るようになってから |
| Phase 4 | `area` / `home_base` / `travel_minutes_to_sanga_stadium`。当日プランの逆算とセットで |

先に器だけ作ると、使われない設定項目が増えます。**扱うデータが増えたタイミングで、必要になった項目だけ足します。**

## 情報収集アーキテクチャ

万能スクレイパーは作りません。

```text
SANGA公式
   │
   ├─ チケット販売表 ──→ ルールベースParser ──┐
   │                                            │
   ├─ 試合ページ ─────→ ルールベースParser ──┤
   │                                            ├─→ Event Candidates
   └─ ニュース記事 ───→ AI抽出 ────────────┘
                                                │
                                                ↓
                                      重複排除 / 変更検知
                                                │
                                                ↓
                                          人間レビュー
                                                │
                                                ↓
                                     calendar-events.json
                                                │
                          ┌─────────────────────┴────────────────────┐
                          ↓                                          ↓
                 Supporter Timeline                          Google Calendar
                                                         （必要なものだけ）
```

重要: Google Calendarを「最終目的」にしません。タイムラインを正本にし、Calendarは出力先の一つとして扱います。

取得については、公式サイトの利用条件と負荷への配慮を先に確認します。取得可否が確認できない範囲は、手入力運用で始めます。
出典URLと確認日は必ず残します（`AGENTS.md` の「公開情報更新時は可能な限り出典URLと確認日を残す」）。

## AI利用方針

ローカルLLM中心でコストを抑えます。

| 段階 | 処理 | AI |
| --- | --- | --- |
| 1 | 構造化ページ | 使わない |
| 2 | 記事本文抽出 | 使わない |
| 3 | 日時候補抽出 | 正規表現中心 |
| 4 | 意味付け・JSON化 | Qwen 7B/14B |
| 5 | 難解記事 | クラウドLLMへフォールバック |

クラウドLLMは全記事ではなく、低確信度や訂正記事など一部だけに限定します。

LLMには「抽出」より「意味付け」を任せます。

- この日時は販売開始か、締切か
- どの試合に関係するか
- 新規イベントか、既存イベントの変更か
- 複数イベントを分割する
- JSONスキーマに整形する

評価の進め方: まずQwen 7Bと14Bで30〜50記事を比較し、日時Recall・変更判定・誤イベント生成・JSON安定性を測ります。
比較結果は本文書か別の調査記録に残し、選定理由を追えるようにします。

抽出処理はローカルまたは運用者の手元で実行し、GitHub Actionsの必須検証には載せません。
APIキーなどの認証情報はリポジトリに置きません（`AGENTS.md` の最重要ルール）。

## 変更検知

「8/22 → 8/30へ変更」を新規2件にしません。

```text
既存イベント          新記事               判定
柏戦 / 一般販売  →   柏戦 / 一般販売  →  UPDATE候補 → 人間確認 → 既存Eventを更新
8/22 12:00           8/30 12:00
```

同一性の判定は、`id`（`種別-試合ID-識別子`）を安定キーとし、本文由来の内容ハッシュを併用して差分を検出する方式を想定します。
「同一性キー＋内容ハッシュ」の考え方自体は本リポジトリ外の実装で用いた方式で、本リポジトリには該当コードはありません。
実装時は既存の `tools/asset-versions.mjs`（内容ハッシュで版数を決める仕組み）が参考になります。

## 管理画面

Human-in-the-loopを前提にします。

- 「新しく見つかった情報 8件」のような候補一覧を出す。
- 各候補に [承認] [修正] [無視]。
- 変更候補は「8/22 12:00 → 8/30 12:00」のように差分を示し [更新する]。
- いつ、どのニュースから、どのイベントを登録・修正したかを更新ログとして残す。

これにより、AI誤抽出がそのまま公開されない状態を保ちます。
管理画面は運用者向けであり、公開ページからはリンクしません（`docs/roadmap.md` の「本番ページから検証用プロトタイプへリンクしない」）。

## 表示カテゴリ

ACTION と INFORMATION を分離します。

| 分類 | 例 |
| --- | --- |
| ACTION | チケット購入、応募、引換、並ぶ、移動する |
| INFORMATION | 開門、イベント開始、ウォームアップ、キックオフ |
| PERSONAL | 家を出る、食事、座席へ移動 |

トップ画面はACTIONを優先し、その下に全体タイムラインを表示します。
分類は色だけで表さず、ラベルまたはアイコンと併記します（`AGENTS.md` の実装上の保護事項）。

## 段階実装

最初から全部のニュースをAI解析しません。

| Phase | 実装内容 | 完了条件の目安 |
| --- | --- | --- |
| Phase 1 | TimelineEventスキーマ / タイムラインUI / チケット販売ページParser / `matches.json` 連携 / LocalStorage MY予定 | `experiments/` のプロトタイプが実データで動き、`tools/validate-calendar-events.js` が通る |
| Phase 2 | ニュース記事収集 / Qwen抽出 / 管理画面 / 人間承認 / 変更検知 / プロフィール（会員種別） | 誤抽出が公開前に止まること、更新ログが残ること |
| Phase 3 | ICS出力 / 通知 / PWA / イベント重複警告 / プロフィール（興味タグ） | 出力が正本データと一致すること |
| Phase 4 | 「あなたの試合当日プラン」自動組み立て / 移動余裕時間の警告 / プロフィール（居住地・移動時間） | 当日の動線が1画面で組めること |

UIを伴う変更のため、Phase 1 は `docs/ui-prototype-workflow.md` に従い `experiments/supporter-timeline/` でのプロトタイプから始めます。
公開ページ化する段階で `docs/site-index.md`（入口ページ）と `docs/production-inventory-audit.md`（公開物一覧）を更新します。

Phase 1 を最小で成立させるなら、AI抽出も管理画面も使わず、手入力の `calendar-events.json` とタイムラインUIだけで検証できます。
この最小構成を先に作り、収集の自動化は後から足します。

## 出力先

タイムラインの正本はこのツールのデータで、外部サービスは出力先として扱います。候補は4系統あります。

### カレンダー系

| 方式 | 認証 | 静的ホスティングで可能 | 位置づけ |
| --- | --- | --- | --- |
| ICS購読フィード（`webcal://.../timeline.ics`） | 不要 | 可能 | 第一候補。一度登録すれば以後自動同期。Google / Apple / Outlook すべて対応 |
| ICS単発ダウンロード（1イベント1ファイル） | 不要 | 可能 | 「この予定だけ入れる」導線。実装が最も軽い |
| Googleカレンダーのテンプレートリンク | 不要 | 可能 | クエリ文字列だけで「カレンダーに追加」ボタンが作れる |
| Google Calendar API連携 | OAuth必要 | 不可 | サーバーと認証情報が必要。現在の構成から外れる |

ICS購読フィードが用意できれば、Google Calendar API連携は不要になる可能性が高いと考えます。
API連携を検討するのは、ICSでは実現できない要件が出てからにします。

### 通知系

| 方式 | 実現性 | 備考 |
| --- | --- | --- |
| カレンダーアプリの通知（ICS経由） | 可能 | 通知の仕組みを自前で持たずに済む。当面はこれを基本にする |
| Web Push（PWA） | 構成変更が必要 | 鍵と配信サーバーが要る。静的ホスティングから外れるため Phase 3 で判断する |
| ブラウザ内リマインド | 制約あり | 端末内で完結するが、ブラウザを閉じていると動かない場合がある |
| メッセージアプリ通知 | 要調査 | サーバーと各サービスの審査・仕様確認が必要。現時点では対象外 |

### 機械可読フィード系

- RSS / Atom / JSON Feed: 静的ファイルを置くだけで配信でき、利用者が自分の道具に繋げられる。
- `calendar-events.json` そのもの: 他ツール（Matchday Dashboard、年間スケジュールページ）から読む内部インターフェースでもある。

### 人間向け出力系

- SNS共有用の画像・テキスト（「今週やること」など）。既存の共有画像生成（`docs/screenshot-social-share.md`）を流用できる。
- 試合当日プランの印刷・スクショ用表示。既存のスクショ用表示と同じ考え方。
- ホーム画面ショートカットからの「次にやること」表示。

### 優先順位

1. ICS購読フィード
2. Googleカレンダーのテンプレートリンク（単発追加の導線）
3. JSON Feed / RSS
4. Web Push（構成変更の判断後）

### パーソナライズとの関係

**静的配信のICSフィードは全員に同じ内容を返すため、プロフィールを反映した個人別フィードは作れません。** 対応は次のいずれかです。

| 方法 | 内容 | 評価 |
| --- | --- | --- |
| 条件別に静的フィードを分ける | `timeline-diamond.ics` のようにグレード別へ分割 | サーバー不要。組み合わせが増えると破綻するため、軸は1つに絞る |
| 端末内でICSを生成してダウンロード | 絞り込み結果からその場で `.ics` を作る | 個人条件が外に出ない。ただし自動同期はできず、都度の書き出しになる |
| 個人別URLを発行する | 利用者ごとの購読URL | サーバーと状態管理が必要。現在の構成から外れる |

当面は「全体フィード＋端末内でのICS書き出し」を基本とし、グレード別フィードの分割は必要になってから判断します。

## ホテル提案との接続

リポジトリには、PR #122 で追加されたホテル候補データの生成基盤が残っています。

| 資産 | 状態 |
| --- | --- |
| `tools/hotels/`（楽天トラベルAPIクライアント、内部モデル、公開JSON変換、調査CLI、生成CLI） | 実装済み。ただし `build_match_hotels.py` は実APIを呼ばず固定のサンプルを返す足場 |
| `public/data/hotel-index.json` | 空索引（0件） |
| `public/data/hotels/{match_id}.json` | 未生成 |
| `tools/validate-hotels.js` | 稼働中。`npm run check:data` から常時実行される |
| `docs/hotels-data-schema.md` / `docs/hotels-operation-flow.md` | スキーマと運用手順を定義済み |

### 設計が一致している点

ホテル提案は、SUPPORTER TIMELINE と同じ構造で作られています。

- APIキーは `tools/` 側に閉じ込め、フロントエンドは `public/data/` の静的JSONを読むだけ。
- 索引ファイルと試合別詳細ファイルの2層に分け、必要な試合だけ遅延読み込みする。
- 試合との紐づけは `match_id`。

タイムライン側の `calendar-events.json` も同じ考え方で設計しているため、**データの作り方をそろえられます。**

### 出口としてのタイムライン

ホテル提案は現在、生成基盤だけがあって公開ページ側の出口がありません。
年間スケジュールページには 2026-07-09 に「日程表と直接関係しない情報を表示しない」方針でプレビュー枠を撤去した経緯があります。

**アウェイ遠征における「宿を取る」は、締切のある ACTION イベントです。** タイムラインなら日程表を邪魔せずに置けます。

- 遠征する試合を、プロフィールの `area`（居住エリア）と `match_ids` から判断する。
- 「宿を取る」を ACTION として、試合日から逆算した位置に置く。
- そのイベントから `public/data/hotels/{match_id}.json` を遅延読み込みして候補を見せる。

`docs/fan-tools-research.md` の AWAY PASSPORT や遠征支援系と同じ系統の機能でもあります。

### 再開するときに決めること

`docs/hotels-operation-flow.md` の「今後の実装ポイント」に加えて、次を確定してから実データを公開します。

- スタジアム座標と検索半径。
- 宿泊日ルール（前泊・後泊の判定をキックオフ時刻と居住エリアからどう決めるか）。
- 料金表示の鮮度（静的JSONに価格を含めると古くなる。価格を持たず導線だけにする案も含めて判断する）。
- **アフィリエイトリンクを使う場合の表記。** 使うなら明示が必要で、`docs/source-and-license.md` にも記録する。
- ダミーデータを公開対象に含めない手順（`build_match_hotels.py` 実行後の差分確認）。

現時点では、タイムラインのPhase 1〜2 にホテル提案を含めません。**先にタイムライン単体を成立させ、遠征イベントを扱えるようになってから接続を判断します。**

## 運用と公開の検討事項

設計が成立するかどうかは、実装できるかよりも「続けられるか」「信じてもらえるか」で決まります。
着手前に方針を決めておくべき点を、リスクの大きい順に挙げます。

### 1. 運用が一人で回るか

人間確認を挟む設計にしたため、**確認作業が止まればツールの情報が古くなります。** 着手前に見積もるべき項目です。

- シーズン中、週あたり何件の候補が出るか。
- 1件あたりの確認・修正に何分かかるか。
- 確認できない週があったとき、画面がどう見えるか（古い情報が残るのか、最終更新日を出すのか）。

見積もりが現実的な負荷を超える場合は、AI抽出を強化するより先に**扱う対象を絞る**判断をします。
例えば「チケット販売と応募締切だけ」に限定すれば、件数も判断の難しさも大きく下がります。

### 2. 通知がない段階で価値が出るか

目的は「販売開始を見逃さない」ことですが、Phase 1 と Phase 2 には通知がありません。
**利用者がツールを見に来るのを忘れたら目的を達成できない**という弱点があります。対応の選択肢です。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| ICS出力を前倒しする | Phase 1 に `.ics` 書き出しを含める | 手入力データ＋ICSだけなら小さく作れる。通知はカレンダーアプリに任せられる |
| 再訪のきっかけを別に作る | ホーム画面追加、SNSでの「今週やること」投稿 | 補助的。習慣化には弱い |
| Phase 1 は検証用と割り切る | 価値の検証はPhase 3以降 | 作ったものが使われない期間が長くなる |

現時点では**ICS出力の前倒しが有力**と考えます。作る順番に関わるため、Phase 1 着手前に決めます。

### 3. 誤情報の責任と訂正

日時を扱うツールは、間違えると「買い逃した」という実害につながります。年間スケジュールページより強い扱いが必要です。

- **全イベントに出典URLを表示する。** 出典のないイベントは公開しない。
- 最終確認は公式サイトで行うよう促す導線を常設する。
- 公開後に誤りが判明したときの訂正手順と、訂正をどう見せるか（更新日時、訂正の履歴）を決めておく。
- 免責事項を置く。年間スケジュールページの既存実装に合わせる。

### 4. 情報の書き方と権利

日時そのものは事実ですが、**公式記事のタイトルや本文をそのまま転載すると別の問題になります。**

- イベント名は自分の言葉で要約し、原文へは出典リンクで飛ばす。
- AI抽出は放置すると原文をそのまま写すため、要約を指示に含め、人間確認の観点にも入れる。
- 画像は使わない。使う場合は `docs/source-and-license.md` に由来と利用条件を残せるものに限る。

### 5. 過去イベントと初期表示

タイムラインは放置すると過去のイベントで埋まります。

- 終わったイベントを消すか、畳むか、薄く残すか。
- 画面を開いた瞬間、どこにスクロールしているか（「今」の位置）。
- シーズン終盤に件数が増えたときの初期読み込み範囲とデータ分割。

地味ですが、毎回の使い勝手を直接左右します。プロトタイプで実データを入れて確認します。

### 6. 年間スケジュールページとの導線

役割は分けましたが、**利用者はどちらを開けばよいか迷います。**

- 試合カードから、その試合に関するタイムラインへ移動できるようにする。
- タイムラインの試合イベントから、試合カードへ戻れるようにする。
- 入口ページ（`docs/site-index.md`）の説明文を、2つのツールで書き分ける。

### 7. 公開の形とスコープ外

- 公開パス（`public/timeline.html` など）、`docs/site-index.md` への追加、OGP、メタ情報。
- 本番反映は `docs/deploy-policy.md` と `docs/operation-flow.md` に従う。
- **やらないことを明示する。** 順位表、移籍情報、リアルタイム速報、選手個人の動向は対象外とします。
  スコープ外を書いておかないと、要望のたびに範囲が広がります。

## 成功条件

- 販売開始を見逃しにくい。
- 1画面で直近行動がわかる。
- 別試合の予定も混在表示できる。
- 試合当日の動線を組みやすい。
- 公式記事を何本も開かなくてよい。
- AI誤抽出がそのまま公開されない。
- 自分に該当する先行販売が、自分で調べなくても分かる。
- プロフィール未設定でも使える。

設計上の最重要ポイントは、「AIで公式情報を完璧に全部拾う」ことを成功条件にしないことです。
まず安定して取得できる構造化情報から始め、ニュースは候補抽出＋人間確認で段階的に広げます。
これにより、情報収集精度が100%でなくてもツール全体が成立します。
