## この文書の目的

京都サンガF.C.の公式情報に散在する「チケット販売」「応募締切」「試合日イベント」「開門」「キックオフ」などを、
サポーター本人の時間軸に統合する非公式ツール `SANGA SUPPORTER TIMELINE` の企画設計を記録します。

現時点では企画・設計の記録のみで、実装、依存追加、公開HTML/CSS/JavaScript変更、公開JSON変更は行っていません。

閲覧用の元資料（HTML）は `docs/concept/supporter-timeline-design.html` です。内容の正本は本文書とします。

## 位置づけ

本企画は、`docs/service-scope.md` で「ニュース連動カレンダー」として構想していたサービスの後継です。
対象とする情報（チケット販売開始、ファンクラブグレード別販売開始、イベント申込開始・終了、グッズ販売、キャンペーン締切）は同じですが、
主表現をカレンダーではなく時系列タイムラインに変え、Google Calendarを出力先の一つに格下げした点が異なります。

| 観点 | ニュース連動カレンダー（従来構想） | SUPPORTER TIMELINE（本企画） |
| --- | --- | --- |
| 主表現 | 公開カレンダー | 1本のサポータータイムライン |
| 利用者の操作 | 必要な予定を自分のカレンダーへコピー | 画面上で次の行動と当日の流れを確認 |
| Google Calendar | 最終出力先 | 出力先の一つ |
| 個人の予定 | 対象外 | 公式イベントと同じモデルで同じ時系列に並べる |
| 日時抽出 | 公式ニュースから抽出＋人間確認 | 同じ（構造化ページを先、ニュースを後） |

役割分担の考え方（年間スケジュールページは試合予定・パーソナライズ・SNS共有に集中し、ニュース由来の日時は別サービスで扱う）は
`docs/service-scope.md` のまま引き継ぎます。名称と主表現の変更は本文書を正とし、`docs/service-scope.md` からも参照します。

#### なぜこの順か

**Fが先なのは、CにもFが要るからです。** いまのICSは UID を
`ticket-{試合}-{販売段階}@sanga-timeline.invalid` という**中身に依存しない形**で作っており
（`tools/generate-calendar-events.js`）、同じ予定だと識別できる土台はあります。
足りないのは版番号で、**`SEQUENCE` が無いとカレンダーアプリは「更新」と判断できません**。
版は `calendar_sequence` / `calendar_last_modified` としてイベントに持たせています
（2026-08-29に実装）。**前回の生成物と見比べ、カレンダーに出る項目が変わった予定だけ
版を上げます**（2026-09-03に変更）。当初は取得時刻から作っていたため、中身が変わって
いない予定でも取り直しただけで版が上がり、購読フィードにすると毎回全件が更新扱いに
なるところでした。詳細は `experiments/supporter-timeline/README.md` の「版」に書いています。
無い場合の挙動はアプリごとに割れ（無視される／二重に入る）、当てにできない。
これはファイル書き出しでも購読フィードでも同じなので、**どちらか一方の応急処置ではなく共通の土台**です。

**Fだけでは足りない部分があります。** 販売が中止・延期になったとき、**すでに利用者の
カレンダーに入った予定を、配ったファイルから取り消す手段はありません。** 相手の端末にあるものに
こちらから手が届かない。これはCでしか解けません（フィードに `STATUS:CANCELLED` で残す）。

#### ファイル書き出しと購読フィードは両方残す

置き換えではありません。**別の欲求に応えています。**

| | ファイル書き出し | 購読フィード |
| --- | --- | --- |
| 誰の予定 | 絞り込んだ結果。MY予定も含められる | 全件・公開データのみ |
| いつ届く | 押したとき | 一度設定すれば以後ずっと |
| 更新・取り消し | 更新は届く（F後）。取り消しは届かない | どちらも届く |
| 準備 | 不要 | 購読の設定が要る |

「今すぐ自分のぶんだけ」と「放っておいても最新」は別のもので、一方に寄せると片方が不便になります。

## 解決したい課題

公式情報が「時系列」でつながっていません。

- チケット販売開始が別ページ・別記事にある。
- イベント開始時刻が試合ニュースの本文に埋もれる。
- 応募締切・引換開始・グッズ販売なども別管理になっている。
- 試合当日の「どの順で動くか」は利用者が自分で組み立てる必要がある。
- 結果として「販売開始を忘れた」「イベントが重なった」「座席に戻る時間が足りない」が起きる。

## 設計原則

主役は「試合」ではなく「サポーター本人」です。すべての情報を、試合単位ではなく1本のサポータータイムラインに並べます。

- 表示の絞り込み軸: ALL / チケット / 応募 / 試合当日 / MY予定
- 各イベントに `match_ids` を持たせ、必要なときだけ特定試合へ絞り込む。
- 公式情報と個人の予定を同じモデルで扱い、UI上は同じ時系列に並べる。
- 情報の正本はタイムライン側のデータとし、Google Calendarなど外部は出力先として扱う。
- 誰向けの情報かは、イベント側に事実として持たせ、利用者の属性との照合は端末内で行う。

## 体験イメージ

「次にやること」と「全体タイムライン」を分けます。

- 次にやること（1件）: 例）明日 12:00 / 🎫 柏戦 SC最速先行販売 / あと13時間
- 全体タイムライン（時系列）: 例）
  - 8/27 12:00 🎫 柏戦 SC最速先行販売開始（公式 / ACTION）
  - 8/29 16:30 🎪 水戸戦 ○○イベント受付開始（公式 / INFORMATION）
  - 8/30 17:10 👤 ○○ブースへ（MY予定）
  - 8/30 19:00 ⚽ 水戸戦 KICK OFF（公式 / MATCH）

## 情報モデル

`TimelineEvent` を最小単位にします。キー名は既存の公開JSON（`public/data/matches.json`）に合わせてスネークケースを使います。

```json
{
  "id": "ticket-sec03-sc",
  "starts_at": "2026-08-30T12:00:00+09:00",
  "ends_at": "",
  "date_precision": "datetime",
  "date_candidates": [],
  "type": "ticket",
  "title": "SC最速先行販売開始",
  "source": "official",
  "action_type": "action",
  "match_ids": ["sec03"],
  "source_checked_at": "2026-08-27",
  "status": "confirmed",
  "is_visible": true
}
```

| キー | 値 | 補足 |
| --- | --- | --- |
| `id` | イベント固有ID | `種別-試合ID-識別子` を基本にし、重複排除・変更検知の同一性キーにする |
| `starts_at` | ISO 8601（`+09:00` 付き） | 確定していない場合は空文字。確からしさは `date_precision` で表す |
| `date_precision` | `datetime` / `date` / `candidates` / `unknown` | 日時の確からしさ（後述） |
| `date_candidates` | 日付の配列 | `date_precision` が `candidates` のときに使う。`matches.json` と同じキー名 |
| `ends_at` | ISO 8601または空文字 | 申込期間・イベント開催時間帯を持つ場合に使う |
| `type` | `ticket` / `entry` / `event` / `goods` / `match` / `personal` | 表示の絞り込み軸に対応させる |
| `source` | `official` / `personal` | 将来 `jleague` などを足せるようにする |
| `action_type` | `action` / `information` / `personal` | 表示カテゴリ（後述） |
| `match_ids` | 試合IDの配列 | 0件・1件・複数件を許可し、クラブ全体イベントにも対応する |
| `source_url` | 出典URL | 誤情報対策として全イベントに必須。公開画面でもリンクとして表示する |
| `status` | `confirmed` / `tentative` | `docs/data-schema.md` の状態語彙に揃える |
| `is_visible` | 真偽値 | `matches.json` と同じく公開制御に使う |

MY予定（利用者自身の予定）も同じモデルで扱います。

```json
{
  "id": "my-seat-sec03",
  "starts_at": "2026-08-30T18:10:00+09:00",
  "type": "personal",
  "title": "座席へ移動",
  "source": "personal",
  "action_type": "personal",
  "match_ids": ["sec03"]
}
```

MY予定は個人状態のためLocalStorage側で扱い、公開JSONには含めません（`AGENTS.md` の保護事項、`docs/personalization.md` に従う）。
LocalStorageキーは既存の命名に合わせ、`sanga-timeline-personal-events-v1` のような `sanga-<機能>-<用途>-v1` 形式を使います。
既存の `sanga-schedule-*` キーは変更しません。

### 日時の確からしさ

`matches.json` の実データでは、**57試合のうち28試合が未確定で、18試合は候補日が複数、19試合は日付そのものが未定、
28試合はキックオフ時刻が空**です。未定は例外ではなく、およそ半分を占めます。タイムラインは最初からこれを前提にします。

| `date_precision` | 意味 | タイムライン表示 | ICS出力 |
| --- | --- | --- | --- |
| `datetime` | 日時とも確定 | 通常どおり時系列に置く | 出す（時刻付き） |
| `date` | 日付のみ確定、時刻未定 | その日の先頭に「時刻未定」として置く | 出す（終日イベント） |
| `candidates` | 候補日が複数 | 最も早い候補の位置に置き、「2/13 or 2/14」のように併記する | **出さない** |
| `unknown` | 日付未定 | 時系列に混ぜず、「日程未定」の別枠にまとめる | **出さない** |

**確定していない日時をICSに出しません。** 購読カレンダーに入った予定は利用者にとって確定情報として届くため、
候補日を流すと誤情報になります。確定したらフィードに自動で現れる、という挙動のほうが信頼できます。

表示は既存の年間スケジュールページに揃えます。同ページは候補日が複数なら両方を並記し、なければ「未定」と表示し、
`tentative-date` クラスで視覚的に区別しています（`public/assets/app.js`）。

なお、日程が未定なのは主に試合そのものです。チケット販売日時は日付が決まってから告知されるため、
このツールの主役である ACTION イベントはほとんど `datetime` になる見込みです。

## 既存データとの整合

タイムラインは新規データを持ちますが、試合そのものの正本は既存のまま `public/data/matches.json` です。

- 試合IDは `matches.json` の `id`（現在は `sec01` 〜 `sec38` 形式）をそのまま外部キーとして使います。
  独自のID体系（`2026-j1-kashiwa-home` のような形）は作りません。
  カップ戦・ACL戦への拡張が必要になった場合は、`docs/service-scope.md` と `docs/data-schema.md` が想定する
  `j1-sec01`、`lev-r1` 形式への移行に合わせます。
- タイムライン側の公開データファイル名は、`docs/service-scope.md` の予告に合わせて `public/data/calendar-events.json` を第一候補とします。
  ファイル名を変える場合は `docs/service-scope.md` と `docs/data-schema.md` も同時に更新します。
- **試合日が候補のままでも、チケット販売日時は確定して告知されます。** 2026-08-28の実データでは、
  開催日が「2/13 or 2/14」の第21節にも、2027-01-16からの8件が日時つきで載っていました。
  「試合が未確定ならぶら下がるイベントも未確定」ではありません。`date_precision` は試合とイベントで
  別々に持ちます（試合は `candidates`、販売は `datetime`）。
- 販売日時が出ないのは、開催日そのものが未定の試合（実データで3件）と、販売スケジュールの記載がない
  試合（同1件）です。この場合は `date_precision: unknown` の情報イベントとして「販売日程は未告知」を置き、
  日程未定の枠にまとめます。
- 公開データを追加する場合は、既存の検証の作り（`tools/validate-matches.js`、`tools/validate-players.js` など）に倣って
  `tools/validate-calendar-events.js` を用意し、`npm run check:data` から呼びます。検証なしで公開データを増やしません。

## タイムラインの見せ方

実データを入れて分かったのは、**情報が正しくても、並べ方次第で読めなくなる**ことでした。
2026-08-28に次を決めました。

**量の問題は実データを全部入れて初めて見えました。** ホーム19試合ぶん（149件）を入れると、
これからの予定だけで77枚、日付見出しが67個、ページの高さが20,371px（幅430pxで約23画面分）になり、
日付の見出しがカードとほぼ1対1で、まとまりとして機能していませんでした。

### 終わったものは畳む

過去の販売がタイムラインの先頭を占めると、開いた瞬間に見えるのが「もう終わったこと」になります。
**既定では今日以降だけを出し、過去は「終わったもの ◯件を表示する」に畳みます。** 消しはしません。
「あの販売はいつだったか」を後から確かめたい場面があるためです。

### 同時刻に始まるものは1枚にまとめる

先行販売とSC特典チケット引換は、同じ等級なら必ず同じ日時に始まります。別々のカードにすると、
1試合で8枚が並び、同じ時刻が2回続きます。**同じ試合・同じ日時・同じ対象のチケットイベントは1枚にまとめ、**
主となる販売を題に、引換を「同時に 特典チケット引換（ゴールド） も始まります」として添えます。
データは分けたまま、表示だけを束ねます。

### 月で区切り、当月と翌月だけ開く

実データは9か月先まであります。**全部を開いたままでは20,000pxを超えて読めません。**
月ごとに区切り、当月と翌月だけを開き、それ以降は「2026年10月 16件」のように畳みます。
件数を見出しに出すのは、畳んだ中に何件あるかが分からないと開く判断ができないためです。

この折りたたみで、ページの高さは20,371pxから8,454pxになりました。

### 日付の下を試合で区切る

1本の時系列は崩しません。日付の見出しの下に試合名の小見出しを置き、同じ試合の予定を続けて並べます。
**見出しで試合名を出したカードからは、題とメタの試合名を省きます。** 「第7節 柏戦」の下に
「柏戦 ゴールド先行販売 開始」と続くと、同じ語が3回出るためです。

**試合名は、その日に1試合しかなくても白場の帯に出します（2026-08-31 変更）。**
以前は1試合の日だけ日付の行にまとめていました（「9月11日（金） 第7節 柏戦」）が、
実機で見ると**日によって帯が出たり出なかったりして、カードが2種類あるように見えました。**
場所は少し取りますが、規則が一目で読めるほうを採ります。

**帯には試合日も出します。** 上の日付見出しは「その予定が始まる日」で、試合日とは別物です。
先行販売は試合の1か月前に始まることもあり、どの試合のことか日付からは分かりません。

混同を避けるため、**3つとも変えています。**

| | 日付の見出し | 帯の試合日 |
| --- | --- | --- |
| 書式 | `9月11日（金）` | `試合日 9/11（金）` |
| 太さ | 太字 | 標準 |
| 色 | 地の上の白 | 白場の上の薄いグレー |

語（「試合日」）を必ず添えるのは、書式と色だけに頼らないためです。
複数の試合をまとめたブロックでは、どの試合の日か言えないので試合日を出しません。

### 出典は必ず出すが、題より先に目に入らせない（2026-08-31 決定）

出典と確認日はすべてのカードに出します。誤情報対策として外せません。
ただし**濃い色＋常時の下線では、題より先に目に入っていました。** 1枚のカードで一番読ませたいのは
「何がいつ始まるか」で、出典はそれを確かめたくなったときに辿るものです。

- 文字色を `--muted` にし、下線は薄い線（`--line-soft`）にする
- 確認日は少し小さくし、`（2026-08-28確認）` として添える
- hover と focus では色と下線を戻す

**下線を消しません。** リンクだと分かる手掛かりを色だけに頼らせないためです。

### 操作は画面下のメニューに集め、シートで開く（2026-08-28 置き換え）

**以前は「次にやること」だけを画面下のドロワーに置いていました。** それはタイムラインが長く、
ページ上部に置くとスクロールした瞬間に見えなくなるためです。この判断は変えていませんが、
**同じ理由が設定や特典チケットにも当てはまることが実機で分かりました。** 上に積むと、
毎回見るタイムラインより先に、一度きりの設定が出てきます。

**操作は画面下の常時メニューに集め、押すとシートが下からせり上がります。** 入れたのは5つです。

| ボタン | 開くもの |
| --- | --- |
| 絞り込み | 種別の絞り込みと「自分に関係するものだけ」 |
| 特典 | 特典チケットの残り枚数・増減・引き換え先 |
| **次にやること** | いちばん近い1件と直近5件（中央・ここだけ塗る） |
| MY予定 | 自分の予定の追加 |
| 設定 | 会員種別とシーズンパス |

**カレンダーへの書き出しだけは見出しの横に置き、見出しごと画面上部に固定します。**
常に見えている必要はあるが押す頻度は低いため、下部メニューの枠を1つ使うのは割に合いません。
**6つ並べると320px幅で4つの文字ラベルが切れることを実測で確かめました**（5つなら全部収まります）。
スクロール中は見出しを帯に縮め、題と書き出しだけを連れて行きます。

**ページはヘッダーの次がタイムラインです。** 日程未定と取り込まなかった記事は、
まれにしか使わないためページ末尾に残しています。

**題の上下にあった文言（`SANGA TOOLBOX` と説明文）は落としました。** 見出しを固定する以上、
帯に残せない行を持っていても場所を取るだけです。検証用である旨とデータの但し書きは
ページ上部の注意書きに集約し、非公式であることは脚注に残しています。

### 初めての人には使い方を出す（2026-08-28 追加）

題の上下の文言を落とした結果、**初めて開いた人に何のツールか伝わらなくなりました。**
説明を見出しに戻すと帯に残せず場所を取るだけなので、**初回だけ出す使い方**にしました。

扱うのは2点だけです。**何ができるか**（公式の予定を1本の時系列に）と、
**どう操作するか**（操作は画面の下から、書き出しは右上）。あいだに、設定すると
自分に関係する予定に印が付くことを挟みます。3枚で終わります。

- 読んだら出しません（`sanga-timeline-tour-v1`）。設定シートの「使い方をもう一度見る」から開き直せます
- 保存を制限されている端末では**出しません**。毎回出るほうが邪魔になるためです
- 説明の図は画面の要素をそのまま小さく作ります。公式由来の画像は使えないためで、
  実物と見た目がずれない利点もあります
- 開いた直後のフォーカスは「次へ」に置きます。既定では最初の「スキップ」に当たり、
  Enterで飛ばしてしまうためです

題の左には**入口ページのキャラの円形・紫版**を置きました。入口ページは五角形（薄紫）と
角丸四角（シアン）の2体で、目のまばたきが共通の作りです。同じ目の作りをそのまま使い、
形を円・色を紫にして家族に揃えています。配色は**目が円のどこに来ても見え、円が地から浮く**
ことを基準に選びました（目と最も暗い部分で3.59、円と地で3.85。装飾の基準3:1を満たす）。

シートは `<dialog>` で開きます。Esc・フォーカスの閉じ込め・閉じたあとのフォーカス復帰は
`<dialog>` の挙動をそのまま使い、出入りの動きと背面のスクロール止めだけを足しています。
動きは `prefers-reduced-motion` と `data-motion="off"` で止まります。

**設定を促す表示は、メニューの「設定」に点で残しました。** 設定は促すが必須にしない、という
「表示の原則」を、設定をシートへ移したあとも保つためです。点は装飾で、読み上げ用の語を併記します。

下部固定はアドレスバーやホームバーと干渉しやすいところですが、`env(safe-area-inset-bottom)` と
`max-height: 84vh` で足りることを2026-08-28にiPhone Safariの実機で確認しました。
「次にやること」は6件目以降を件数だけ伝えてタイムラインへ送ります
（「ほか35件はタイムラインで見られます」）。

**1件だけでは足りないことも実データで分かりました。** 直近1週間に複数の販売と締切が並ぶため、
「次にやること」が1件では、その次を見るのにタイムラインを探すことになります。

### 種別はイラストと文字で示す

チケット・応募・イベント・グッズ・試合・MY予定を、それぞれの形のアイコンで示します。
**アイコンは装飾で、`aria-hidden` にします。** 文字ラベル（「チケット」など）は残すため、
読み上げでは文字が読まれ、目で見るときは形で種別が分かります。
この作りは2026-08-28にiPhone Safariの実機で確認しました。
`★` や `◎` のような記号を文字として置く方法は取りません（「特典チケットの管理」節）。

### 設定は畳んで本体を近づける（2026-08-28 置き換え済み）

**この節は「操作は画面下のメニューに集め、シートで開く」に置き換わりました。** 当時は設定を
ページ上部に置いたまま折りたたんでいましたが、畳んだ見出しが3つ先に並ぶ形は残っていました。
いまは設定そのものを画面下のシートへ移しています。

折りたたみ自体は特典チケットのシートの中にだけ残しています。1枚のシートに複数のフォームが
入るためです。設定とMY予定はシート自体が折りたたみなので、中の折りたたみは無くしました。

### 地は入口ページのネビュラ、内容は白場に載せる（2026-08-28 決定）

本番移植にあたって、**入口ページ（`public/assets/index.css`）を基準にすることを決めました。**
3つの公開ページはそれぞれ別の紫を持ち、共有しているのは `#7b0064` だけで、統一された
デザインシステムはありません。そのなかで入口ページを選んだのは、`--radius` と `--tap` を
持つ唯一のページで、`rem` とトークンで書かれているためです。年間スケジュールは `px` 固定で
6pxの文字を持つため、真似ると読みやすさが後退します。

背景は入口ページの二層構成をそのまま借ります。WebGLのネビュラ（`startNebula`）が使えれば
それを敷き、使えなければCSSのぼかしが残る進行的強化です。プロトタイプは
`public/assets/index-nebula.js` を直接読み込んで確かめています。

**その上に、内容を白場（`.block`）に載せます。** 白場の単位は「その日の・その試合ぶん」で、
月と日付の見出しだけが地の上に出ます。こうすると札と札のあいだで背景が一定の間隔で見え、
149件の情報量を白い面で受けられます。**月見出しは細い罫線では地に沈んだため、紫の帯にしました。**

原則は「**内容は白場、構造は地**」です。日程未定の一覧と取り込まなかった記事も内容なので
白場に載せます。地の上に置いた紫のリンクは背景と同化して読めませんでした。

#### 地の上の文字は実測で決める

ネビュラは明るさが動くため、地の上の文字色は最も明るい部分を基準にします。
実測した最明部は `#a23c88` で、そこに対する比は次のとおりでした。

| 文字色 | 最明部との比 | 判定 |
| --- | --- | --- |
| `rgba(255,255,255,0.72)`（入口ページの `--ink-dim`） | 3.86 | 本文には不足 |
| `rgba(255,255,255,0.86)` | 4.84 | 満たす |
| `#6fd6e8`（`--cyan-soft`） | 3.52 | 本文には不足 |

**入口ページより明るい 0.86 を使います。** 入口ページの `--ink-dim` は短いラベル向けで、
こちらは地の上に本文が乗るためです。補助テキストとリンクの色は面ごとに切り替え、
白場のなかでは濃いグレーと `--accent` に戻します（`--muted` と `--link` を白い面で再定義）。

## サポータープロフィール

同じ公式情報でも、次に取るべき行動は人によって違います。ファンクラブのグレードが違えば先行販売の開始日時が違い、
居住地が違えばアウェイ戦の位置づけが違い、興味が違えば見たいイベントが違います。
タイムラインを「自分の時間軸」にするには、この属人的な条件を扱う必要があります。

### 何を持つか

`SupporterProfile` を利用者ごとに1件だけ持ちます。すべて任意入力で、未設定でもタイムラインは成立させます。

```json
{
  "fc_grade": "",
  "has_season_ticket": false,
  "area": "",
  "home_base": "",
  "interests": [],
  "travel_minutes_to_sanga_stadium": null,
  "updated_at": "2026-08-27"
}
```

| キー | 値 | 何に効くか |
| --- | --- | --- |
| `fc_grade` | `platinum` / `gold` / `regular` / `kids` / `none` | 自分に該当する先行販売の開始日時だけを「次にやること」に出す |
| `has_season_ticket` | 真偽値 | シーズンパス先行販売に該当するかの判定 |
| `area` | 居住エリアの粗い区分（例: 京都市内 / 京都府内 / 関西 / その他） | HOME中心かAWAY遠征中心かの重み付け、近隣アウェイの判定 |
| `home_base` | 出発地の目安（駅名などの選択肢） | 当日プランでの移動時間の逆算（Phase 4） |
| `interests` | 興味タグの配列（例: `goods` / `event` / `kids` / `away` / `collect`） | イベント種別の並べ替えと絞り込み |
| `travel_minutes_to_sanga_stadium` | 分（整数） | 「家を出る」時刻の逆算の初期値 |

**シーズンパスは会員種別とは別の軸です。** SANGA CREW の等級（プラチナ / ゴールド / レギュラー / キッズ）と
シーズンパスの保有は独立しており、「ゴールドクルーでシーズンパス保持者」も成立します。
その人にとっては先行販売が2回あることになるため、`fc_grade` の値としてではなく `has_season_ticket` として別に持ちます。

**自由入力の住所、氏名、会員番号、連絡先は持ちません。** 保存するのは選択肢のコードだけです。
居住地も番地レベルではなくエリア区分にとどめ、必要になった時点で粒度を上げるか判断します。

### どこに保存するか

`docs/personalization.md` の方針どおり、LocalStorageに保存し、公開JSONには一切含めません。

- キーは `sanga-timeline-profile-v1`（`sanga-<機能>-<用途>-v1` 形式）。
- 既存の `sanga-schedule-*` キーとは分けます。既存キーは変更しません。
- 保存内容削除ボタンの対象に含め、何が消えるかを画面上で明示します。
- 端末を変えると消えるため、書き出し・読み込み（JSONのコピー＆貼り付け）を早い段階で用意します。

プロフィールはサーバーへ送りません。照合はすべて利用者の端末内で行います。
この方式なら、個人の属性がどこにも記録されないまま、パーソナライズだけが成立します。

### イベント側に持たせる条件

プロフィールと突き合わせるため、`TimelineEvent` に「誰向けか」を持たせます。

```json
{
  "id": "ticket-sec07-gold",
  "starts_at": "2026-08-28T12:00:00+09:00",
  "type": "ticket",
  "title": "柏戦 ゴールドクルー先行販売開始",
  "audience": { "fc_grade": ["gold"] },
  "interest_tags": [],
  "match_ids": ["sec07"]
}
```

| キー | 意味 |
| --- | --- |
| `audience` | このイベントが該当する条件。空または未指定なら全員向け |
| `audience.fc_grade` | 該当する会員種別コードの配列 |
| `audience.season_ticket` | 真偽値。シーズンパス保持者向けの販売であることを示す |
| `interest_tags` | 興味タグ。`interests` と突き合わせて並べ替えに使う |

イベント側が持つのは「事実」（このグレードの販売はこの日時）だけです。「誰に見せるか」の判断は端末内の照合に任せます。

会員種別は「SANGA CREW」の4コース（プラチナクルー / ゴールドクルー / レギュラークルー / キッズクルー）に対応し、
コードは `platinum` / `gold` / `regular` / `kids` とします。非会員は `none` です。
プラチナクルーは定員制で受付を終了している時期があるため、実際の分岐は `gold` / `regular` / `none` が中心になる見込みです。

### 販売段階は8つある（2026-08-28 実データで確認）

1試合のチケット販売は、**先行販売5段階とSC特典チケット引換3件の、合わせて最大8件**に分かれます。
公式のチケット販売スケジュールを2026-08-28に確認した結果です。スナップショットは
`docs/sheets/ticket-sales.2026-08-28.csv`（124行）にあります。

| 段階 | 時刻 | `audience` |
| --- | --- | --- |
| シーズンパス先行受付（ホーム指定席購入者） | 11:00 | `{ "season_ticket": true }` |
| プラチナ先行販売 | 12:00 | `{ "fc_grade": ["platinum"] }` |
| 特典チケット引換（プラチナ） | 12:00 | `{ "fc_grade": ["platinum"] }` |
| ゴールド先行販売 | 12:00 | `{ "fc_grade": ["gold"] }` |
| 特典チケット引換（ゴールド） | 12:00 | `{ "fc_grade": ["gold"] }` |
| レギュラー・キッズ先行販売 | 12:00 | `{ "fc_grade": ["regular", "kids"] }` |
| 特典チケット引換（レギュラー・キッズ） | 12:00 | `{ "fc_grade": ["regular", "kids"] }` |
| 一般販売 | 12:00 | `{}`（全員向け） |

**この8件が全部タイムラインに並ぶことが、プロフィールを必要とする理由です。** 自分に関係するのは
このうち1〜3件で、残りは見なくてよい情報になります。プロトタイプの実データ5試合分では、
全40件がゴールドクルー設定で20件まで減りました。

実データから分かったことは次のとおりです。

- **プラチナクルーの先行販売は現行シーズンにも存在します。** 「定員制で受付を終了しているため
  実際の分岐は `gold` / `regular` / `none` が中心になる」という以前の見込みは、販売スケジュール上は成り立ちません。
  4等級すべてに販売日時があるため、`fc_grade` の選択肢から `platinum` と `kids` を落としません。
- **特典チケット引換は先行販売と同時刻です。** 同じグレードの2件が必ず同じ日時に並びます。
- シーズンパス先行受付だけ11:00で、他はすべて12:00です。
- 先行販売は2日おきに1段階ずつ進み、一般販売はレギュラー・キッズ先行の翌日です。
- 掲載は試合単位です。2026-08-28時点で15試合分が掲載済み、4試合分が未掲載でした。

`audience` に複数のキーがある場合は、**いずれかを満たせば該当**として扱います。

**特典チケットを持っているかどうかは、まだモデル化していません。** 引換の対象は「特典チケットを
保有するその等級の会員」ですが、プロフィールは等級しか持たないため、等級が一致すれば引換にも印が付きます。
保有の有無を持たせるか（`has_benefit_ticket`）はPhase 3の判断材料とし、現時点では等級で照合します。

### 表示の原則

**既定は「隠す」ではなく「並べ替えと強調」です。**

- 自分に該当するイベントを上に出し、印で理由を示す（例: 「あなたのグレードが対象」）。
- 該当しないイベントも一覧からは消しません。プロフィールの設定ミスや、家族分の購入など、
  自分の属性と関係なく知りたい場合があるためです。
- 明示的に「自分に関係するものだけ」を選んだときだけ絞り込みます。
- プロフィール未設定でも全イベントが見えます。設定を促す表示は出しますが、必須にしません。
- 強調は色だけに依存させず、読み上げて意味が通る言葉で示します。記号（`★` `◎`）は使いません。

### 段階

| Phase | 扱う項目 |
| --- | --- |
| Phase 1 | なし（プロフィールなしでタイムラインが成立することを先に確認する） |
| Phase 2 | `fc_grade` と `has_season_ticket`。プロトタイプで実装済み（2026-08-28） |
| Phase 3 | `interests`。イベント種別が増えて絞り込みが要るようになってから。特典チケットの管理はPhase 2で先に入れた（枚数は属性ではなく状態のため、プロフィールとは別に持つ） |
| Phase 4 | `area` / `home_base` / `travel_minutes_to_sanga_stadium`。当日プランの逆算とセットで |

先に器だけ作ると、使われない設定項目が増えます。**扱うデータが増えたタイミングで、必要になった項目だけ足します。**

## 特典チケットの管理

**SC特典チケットは「いつ引き換えるか」「引き換えたか」がどこにも残りません。** 公式サイトに出るのは
引換開始日時だけで、自分が何枚持っていて、どの試合に充てるつもりかは、会員本人の記憶の外に置き場がありません。
シーズン終了とともに価値が消えるため、**計画を立てられないこと自体が損失につながります。**

タイムラインは試合日程を持っているため、「残り枚数」と「これから引き換えられるホーム戦」を突き合わせられます。
これは既存のどのツールにもない情報です。

### 「使う」ではなく「引き換える」

特典チケットは、**試合のチケットに引き換える**方式です。入場したかどうかとは別の行為であり、
引き換えた時点で1枚が消費されます。画面の文言も保存する状態も「引き換える予定」「引き換えた」で統一します。
実際に入場したかは、このツールでは扱いません。

### 何を持つか

公式には個人の保有状況が出ないため、**利用者の自己申告として端末内に持ちます。**

**枚数は1つの数ではなく、理由つきの増減の履歴で持ちます。** 家族の分をまとめて持っていたり、
友人と譲り合ったりするため、「いま何枚か」だけでは自分の記録を信用できなくなります。
合計は履歴から計算します。

```json
{
  "changes": [
    { "id": "chg-1", "count": 3, "reason": "grant", "note": "", "at": "2026-08-28" },
    { "id": "chg-2", "count": 2, "reason": "received", "note": "家族から", "at": "2026-08-28" },
    { "id": "chg-3", "count": -1, "reason": "given", "note": "友人へ", "at": "2026-08-28" }
  ],
  "uses": [
    { "match_id": "sec07", "count": 2, "status": "planned", "updated_at": "2026-08-28" }
  ],
  "updated_at": "2026-08-28"
}
```

| キー | 意味 |
| --- | --- |
| `changes[].count` | 増減の枚数。増やす場合は正、減らす場合は負 |
| `changes[].reason` | `grant`（会員特典として受け取った） / `received`（譲り受けた） / `given`（譲った） / `correction_plus` / `correction_minus` |
| `changes[].note` | 任意のメモ（30字まで）。「家族から」など |
| `changes[].source_grade` | 譲り受けた特典の持ち主のコース。`received` のときだけ持つ。分からない場合は空 |
| `changes[].at` | 記録した日 |
| `uses[].match_id` | 引き換える試合。`matches.json` の `id` をそのまま外部キーにする |
| `uses[].count` | その試合に充てる枚数。**1試合に複数枚まとめて引き換えられます** |
| `uses[].status` | `planned`（引き換える予定）または `exchanged`（引き換えた） |

持っている枚数 = `changes[].count` の合計。残り = 合計 −（引き換える予定 + 引き換えた）です。
**譲渡は引き換えではないため、`uses` ではなく `changes` に負の値で入ります。** 引き換えの履歴と
保有の増減を混ぜないことで、「何枚を誰に渡したか」と「何枚を試合に充てたか」を別々に追えます。

理由は選択肢から選ばせ、符号は理由が決めます。メモは任意で、端末から出ません。

### 引換の枠は「チケットの持ち主のコース」で決まる

**先行販売と引換で、家族の扱いが違います。**

先行販売は上位コースの枠で買えば足ります。家族に下位コースの人がいても、早いほうで買えばよく、
遅い枠が見えなくても損をしません。**プロフィールを家族ぶん持つ必要はありません。**

引換は逆です。**譲り受けた特典チケットは、譲った人のコースの枠でしか引き換えられません。**
ゴールドの人がキッズクルーの家族から1枚もらった場合、引き換えられるのはレギュラー・キッズの枠で、
自分のゴールドの枠では引き換えられません。早い枠に前倒しできないため、
「自分のコース」で突き合わせると引換日時を間違えます。

そのため `changes[].source_grade` に持ち主のコースを持ち、引換の突き合わせは
**持っているチケットのコードの集合**で行います。会員特典として受け取ったぶんと数え直しは自分のコース、
譲り受けたぶんは記録した相手のコースです。どちらも分からない場合は絞り込まず、
3つの枠をすべて出します（安全側に倒す）。

なお SANGA CREW に家族向けのコースはありません（2026-08-31に公式サイトで確認）。
コースは4つ（プラチナ / ゴールド / レギュラー / キッズ）のままです。

### カレンダーには引き換え予定の試合だけ出す

**引換イベントは画面には全件出し、ICSには `uses` に載っている試合の、持っているチケットのコースの枠だけ出します。**

引換は1試合に3件（会員グレード別）あり、ホーム戦19試合ぶんで57件になります。全部カレンダーへ入れると、
使う予定のない予定で埋まります。一方で画面から消すと「どの試合で使えるか」が見えなくなり、
引き換え予定を決める材料がなくなります。**見るための情報と、カレンダーに常駐させる予定は別物**として扱います。

外した件数は書き出し後の文言で知らせます。「日時が未確定だから外した」ものとは分けて書きます。
利用者が次にやること（待つ / 特典で引き換え予定を決める）が違うためです。

LocalStorageキーは `sanga-timeline-benefit-tickets-v1` です。プロフィール（`sanga-timeline-profile-v1`）とは
別に持ちます。**枚数は時間とともに変わる状態であり、会員種別のような属性ではないためです。**
1試合につき1件にまとめ、同じ試合へ足した場合は `count` を合算します。

### 配布枚数と有効期間

`experiments/supporter-timeline/benefit-tickets.json` に、2026-08-28に確認した公式の条件を持ちます。

| コース | 特典チケット | 根拠 |
| --- | --- | --- |
| プラチナクルー | 3枚 | ゴールドの特典を含む構成からの推定 |
| ゴールドクルー | 3枚 | 公式コース詳細に明記 |
| レギュラークルー | 1枚 | 公式概要に明記 |
| キッズクルー | 1枚 | 公式概要に明記 |

有効期間は「2026-27シーズンでのみ使用可能」です。会員期間は2026-07-01〜2027-06-30ですが、
**公式がチケット固有の暦日締切として2027-06-30を明記しているわけではありません。** 実際の期限は
対象ホームゲームの開催日までです。画面には公式の表記をそのまま出し、こちらで日付に言い換えません。

利用条件として「一部対象外の試合が設定される場合がある」「対象席種が完売した場合は利用できない」も
併記します。残り枚数だけを見て引き換えられると誤解させないためです。

1.5シーズン加入者向けの特別シーズンチケット（百年構想リーグ限定・1枚）は、2026-08-28時点で利用期間が
終了しているため扱いません。

### 何を出すか

| 場面 | 表示 |
| --- | --- |
| 残り枚数 | 合計 −（予定 + 引き換え済み）を大きく出す |
| 内訳 | 持っている / 引き換える予定 / 引き換えた の3つ |
| 使わないまま残るおそれ | 残り枚数がこれからのホーム戦数より多いとき、1試合に複数枚まとめる必要があると伝える |
| 引換イベント | 自分の等級の引換イベントに「特典チケットは残り◯枚」を添える |
| 試合 | 充てた試合のキックオフに「特典チケットを◯枚 引き換える予定」「◯枚 引き換えた」を出す |
| 枚数の増減 | 理由とメモつきで新しい順に並べ、1件ずつ取り消せる |
| 配布枚数の案内 | 会員種別を保存していて増減の記録がまだないとき、公式の枚数を初期値として提案する |

日程未定・候補日のホーム戦も「これから引き換えられる試合」に数えます。日程が決まっていないだけで、
引き換えられる機会であることに変わりはないためです。

**印は記号ではなく言葉で示します。** `★` や `◎` は音声読み上げで意味が伝わらないため使いません。
「あなたのグレードが対象」「特典チケットは残り3枚」のように、読み上げてそのまま意味が通る文にします。
視覚的な区別は枠線と背景色で付け、色だけに依存させません（`AGENTS.md` の実装上の保護事項）。

### 決めていないこと

- 引換や入場の実績を知る手段はありません。「引き換えた」は自己申告のままで、取り消しできるようにします。
- 譲渡の相手は記録しません。メモは自由入力ですが、氏名や連絡先を持つ設計にはしていません。
- プラチナクルーの3枚は公式の明記ではなく構成からの推定です（`count_confidence: high`）。
- 対象外の試合と対象席種は試合ごとに変わるため、個々の試合が引き換え可能かまでは判定しません。

## アウェイ戦のチケット

**2026-08-31 時点で、チケット情報があるのはホーム19試合だけです。** アウェイ24試合は空白です。
抜けているのではなく、**取得元がそもそも違います。** 公式のチケット販売スケジュールページは
ホーム戦しか載せません。アウェイ席を売るのは相手クラブだからです。

### なぜ難しいか

**販売元が19クラブに分かれています。** サイトの作りも、先行の段階も、掲載する場所もばらばらです。
19本のスクレイパーを書くのは「万能スクレイパーを作らない」方針に反しますし、
書けたとしても壊れ続けます。

**グレードは関係ありません。** アウェイ席は相手クラブの会員先行か一般販売で、
SANGA CREW の等級は基本的に効きません。`audience` は空（全員向け）になります。
ビジター席にクラブ先行がある試合は例外ですが、それはクラブごとに違い、追いません。

### 情報源

| | 源 | 取れるもの | 判断 |
| --- | --- | --- | --- |
| 近道 | Jリーグチケットの `club/ks/?tab=away` | **そこで売っている発売中の試合**と、その在庫の状態 | **採る。** ただし全試合は載らない |
| 日時 | 同じサイトの試合ページ（`/sales/perform/{id}/001`） | 席種 × 販売区分ごとの販売期間 | **採る。** 静的HTMLに入っている |
| 本命 | 対戦クラブ公式。**直近のアウェイ戦のぶんだけ** | 開始日時。**別サイトで売るクラブはここだけが頼り** | **採る。** 手入力で回る |
| 補助 | サンガ公式ニュース | 開始日時 | 記事がある試合だけ。アウェイ戦の記事は少ない |

Jリーグチケットには**AWAYタブがあり、京都がアウェイの試合が並びます**（`?tab=away`）。
19サイトを回らずに済む唯一の入口です。

**ただし、載るのは発売中の試合だけです。** 2026-08-31に確認したところ、並んでいたのは9件で、
状態はすべて「空席あり」「空席わずか」でした。`発売前` `発売開始` `未定` といった語はありません。
**まだ発売していない試合は、行そのものが現れません。**

#### 試合ページに販売期間があります（2026-08-31 確認）

試合ごとのページ（`/sales/perform/{id}/001`）の「発売情報」に、
**席種 × 販売区分ごとの販売期間が入っています。** 静的HTMLに含まれ、JavaScriptもXHRも要りません。

FC東京戦（アウェイ）から実際に取れた例です。

```text
一般発売／店頭発券（Ｊチケ）              07/27(月)10:00〜
【FC東京】SOCIO限定発売／ＱＲチケット      07/25(土)10:00〜
【FC東京】OMS限定発売／ＱＲチケット        07/26(日)10:00〜
【FC東京】駐車券 SOCIO限定発売／店頭発券    07/25(土)10:00〜
```

分かることは3つあります。

- **一般発売の開始日時**が時刻まで取れます
- **相手クラブの会員先行**が、区分名つきで分かります（FC東京なら SOCIO、OMS）
- **駐車券の販売開始**まで分かります。アウェイ遠征では効きます

書式は開始と終了の組で、発売済みの区分は `〜09/05(土)23:59` と終了だけ、
これからの区分は `07/27(月)10:00〜` と開始が出ます。
取り出し口は `.info-schedule-list .item` の `.title` と `.date` です。

**載っている試合については、相手クラブのサイトを見ずに日時が取れます。**

#### 限界は2つあります

**1つめ。全クラブがJリーグチケットを使っているわけではありません。**
ヴィッセル神戸は楽天チケット、柏レイソルはローソンチケットというように、
自前や別のプレイガイドで売るクラブがあります。**そのクラブがホームの試合は、
発売中でもJリーグチケットに現れません。**

**2つめ。載るのは発売中の試合だけです。** まだ1区分も開いていない試合のページには辿り着けません。
ただし**どれか1区分が開けば、その試合の全区分の開始日時がまとめて読めます。**
先行が開いた時点で一般発売の日時が分かるため、この2つめは多くの場合ふさげます。

2026-08-31に確認した時点で、アウェイタブに出ていたのは横浜FM戦・FC東京戦・岡山戦の3件だけでした。

**したがってJリーグチケットは「全アウェイ戦の土台」ではなく、「取れる試合の近道」です。**
取れない試合が必ず残ります。その扱いを決めておきます。

- **取れない試合を「発売前」と扱いません。** 載っていない理由が、未発売なのか別サイト販売なのか区別できません
- 取れない試合は対戦クラブ公式を見ます。**直近の1〜2試合だけなので、手入力で回ります**
- どのクラブがJリーグチケット以外かは**固定表を持ちません。** クラブは販売先を変えます。
  「載っていなければ相手クラブ公式を見る」という手順だけを持ちます

ACLなど国外のアウェイ戦はJリーグチケットに載りません。対象は国内リーグ戦だけです。

#### 相手クラブは「19サイト」ではなく「次の1つ」

当初は「相手クラブ19サイトはコストが釣り合わない」としていましたが、**前提が雑でした。**

**19クラブを同時に相手にする必要はありません。必要なのは直近のアウェイ戦、せいぜい2〜3試合ぶんです。**
次のアウェイが横浜FM戦なら、見るのは横浜FMのサイト1つです。試合が過ぎれば用済みになります。

- 常設のスクレイパーではなく、そのとき必要なクラブだけを対象にします
- 手入力でも回ります。年24試合、1試合1回です
- 書くとしても1クラブぶんずつで、壊れてもその試合だけが落ちます

これなら「万能スクレイパーを作らない」方針と矛盾しません。

#### 手掛かりと出典を分ける

有志がアウェイ戦の発売日時をまとめてSNSに投稿していることがあります。内容は正確なことが多く、
探す手間を大きく減らします。**ただし、これは一次情報ではありません。**
一次情報はクラブが出したものです。

| | 扱い |
| --- | --- |
| **手掛かり**（SNS投稿、まとめ画像など） | 人が見る。**保存しない**。`source_url` にしない |
| **出典**（クラブ公式のページ） | これだけを保存する |

手順は「気付く → 公式で確認する → 公式のURLと日時を入れる」です。保存されるのは公式の事実だけで、
投稿の文言もURLも画像も残りません。既存の「手入力」経路そのもので、新しい仕組みは要りません。

**公式で確認が取れなかったものは入れません。**

| 状況 | どうするか |
| --- | --- |
| 公式で確認できた | 日時を入れる。`source_url` は公式 |
| 投稿はあるが公式に記載がない | 入れない。または日時なしで扱う |
| 投稿と公式が食い違う | 公式を採る |

**この経路は人力です。** XのAPIは有料で、スクレイピングは規約違反です。
投稿を監視して自動で取り込む形にはできません。

### 「発売中」は予定ではなく状態

ここが判断の中心です。

**在庫の状態を、観測した日のイベントとしてタイムラインに置きません。** 「8月31日 発売中」と出すと、
その日に発売が始まったように読めます。実際には**それ以前のいつかに始まっていて、日時は分かりません。**
1日1回の取得では、状態が変わった日までしか分からず、時刻は取れません。

日時をでっち上げないために、**イベントと状態を別に持ちます。**

| | 持ち方 | 画面 |
| --- | --- | --- |
| 開始日時が分かる（クラブ公式由来） | `events` に普通のイベント | 時系列に並ぶ。カレンダーにも出る |
| 発売中であることしか分からない | `away_tickets` に状態 | 試合の帯に「アウェイ席 発売中（8/31確認）」 |
| どちらも分からない | 何も持たない | 何も言わない |

状態はカレンダーへ出しません。予定ではないためです。

### データの持ち方

生成物に第3のキーを足します。`events` と `skipped` の隣です。

```json
{
  "away_tickets": [
    { "match_id": "sec05", "state": "on_sale", "checked_at": "2026-08-31",
      "source_url": "https://www.jleague-ticket.jp/club/ks/" }
  ]
}
```

| キー | 意味 |
| --- | --- |
| `state` | `on_sale`（買える） / `unknown`（読めなかった） |
| `checked_at` | 確認した日。状態には「いつ時点か」が必ず要る |

**`before_sale`（まだ発売していない）は持ちません。観測できないためです。**
アウェイタブに行が無いことは「発売前」とも「載せていないだけ」とも読めます。
区別できないものを状態として持つと、画面で「発売前」と言い切ってしまいます。
行が無い試合は `away_tickets` に入れず、画面でも何も言いません。

**`public/data/matches.json` には書きません。** 年間スケジュールページの正本であり、
勝手に変更しない対象です（`docs/codex-workflow.md`）。

語彙の追加は**1つだけ**です。開始日時が分かった場合のイベントに `ticket_kind: "away_sale"` を使います。
`source` は増やしません。日時の出どころはサンガ公式ニュースなので `official` のままです。

**試合の対応付けは日付で行います。** Jリーグチケット側の対戦相手表記は「横浜Ｆ・マリノス」、
`matches.json` は「横浜FM」と揃いません。1日に2試合はないため日付が実質の鍵になります。
日付で1件に決まらない場合は取り込まず、`skipped` に残します。**推測で結び付けません。**

## 購読フィード

**固定URLに `.ics` を置き、`webcal:` で購読してもらう仕組み。**（候補C。2026-09-04に設計、未実装）

いまのICSは「表示中の予定をその場で組み立てて渡す」1回きりの取り込みです。販売日時が
変わっても、中止になっても、配ったファイルからは直せません。フィードならカレンダーアプリが
自分で取りに来るので、更新も取り消しも自動で届きます。

前提は #242 で整いました。取り直しただけで全予定の版が上がる状態のままフィードにすると、
購読側では毎回全件が更新扱いになるためです。

### 何を出すか（全部入り1本）

**フィードは1本だけ置きます。** 公開URLひとつなのでプロフィールによる絞り込みができず、
グレード別に分けるなら本数を増やすしかありません。増やす判断は後からでもできますが、
**先に配ったURLの意味を後から変えることはできません。**

本数を増やしたときに利用者が被る不利益を、決め手にしました。

- 移行は全員の手作業になる。こちらから購読先を移すことはできず、告知を見なかった人は古いままになる
- 古いURLは畳めない。使っている人がいる限り出し続けることになり、実質、本数は増える一方になる
- 二重登録が起きる。新しいのを足して古いのを消し忘れると、同じUIDが2本から届き、アプリによっては予定が重複する
- 「どれを選べばいいか」が説明の負担になる。1本なら「これを登録」で終わる

絞り込みとMY予定は、これまでどおり単発ダウンロードが担います。**両方残します。**

### URLは変えない。版数（`?v=`）を付けない

購読者は最初に登録したURLをそのまま持ち続けます。**`.ics` は内容ハッシュによる版数付け
（`tools/asset-versions.mjs`）の対象にしません。** URLが変わった瞬間、既存の購読は
静かに死にます。`.ics` はいま対象拡張子（`css` / `js` / `mjs` / `json`）に入っていないため
自動では拾われませんが、これは偶然ではなく決めごととして守ります。

更新の頻度は `REFRESH-INTERVAL;VALUE=DURATION` と `X-PUBLISHED-TTL` で伝えます。
取りに来る間隔は最終的にカレンダーアプリ側が決めるもので、こちらから強制はできません。
**「登録すれば即座に反映される」とは説明しません。** 数時間から1日遅れることがあります。

### 消えた予定は墓標として残す（試合日の1週間後まで）

いまの生成は「CSVにある行を出す」だけなので、**CSVから消えた予定は出力からも消えます。**
フィードでこれをやると、利用者のカレンダーには消えた予定が残ったままになります。
消すには `STATUS:CANCELLED` の項目として出し続けるしかありません。

一度フィードに載せたUIDは、元が消えても墓標として出し続けます。

- **残す期間は、その予定が結び付く試合の試合日から1週間後まで。** 終わった試合の予定を
  いつまでも配り続けても意味がなく、かといって即座に消すと、その間に同期しなかった端末には
  取り消しが届きません
- 墓標の判断材料は前回の生成物。UIDごとに前回値を読む仕組みは #242 で入っており、そこに乗せます
- 墓標も版を上げます。`STATUS` が変わるのは中身の変化なので、`SEQUENCE` を +1 して
  `LAST-MODIFIED` を更新しないと、取り消しが更新として届きません

### ICSの組み立ては下回りだけ共通化する

フィードとダウンロードは、**やっている仕事が違います。**

| | ダウンロード（`public/assets/timeline.js` の `buildIcs()`） | フィード（これから作る） |
| --- | --- | --- |
| 対象の決め方 | プロフィール・引き換え予定で絞る（LocalStorage を見る） | 絞らない |
| MY予定 | 入る | 入らない（個人の予定を公開ファイルに入れない） |
| 墓標 | 不要 | **必要** |
| 動く場所 | ブラウザ | Node（生成時） |

そこで**「何を出すか」は共通化せず、「どう書くか」だけを共通化します。**

```
public/assets/ics.js      ← icsEscape / 日時の整形 / VEVENT の組み立て（共通）
public/assets/timeline.js ← 誰の何を出すか決めてから ics.js に渡す
tools/build-ics-feed.js   ← 全部入り＋墓標を決めてから ics.js に渡す
```

2本持つと、ダウンロードしたファイルと購読フィードで中身が静かにズレます。利用者から見ると
「同じツールが出した2つのカレンダーの中身が違う」という、いちばん分からない壊れ方になります。

ブラウザ用ファイルをNodeから読む方法は、このリポジトリに前例があります。
`tools/validate-squad-contract.mjs` が `public/assets/squad-formations.js` を
`data:` URL 経由で `import()` しています。同じ型に乗せます。

### 説明ページを厚く作る

**フィードは利用者のカレンダーに残り続けるものなので、説明の手を抜けません。**
ダウンロードなら「消せばいい」で済みますが、購読は登録した本人が解除しない限り消えません。
説明が足りないと、こちらではどうにもできない面倒を相手に残します。

書くこと。

- **登録の仕方をアプリごとに。** Googleカレンダー・Appleカレンダー（iPhone / Mac）・Outlook。
  `webcal:` を押すだけで済む経路と、URLを貼り付ける経路の両方
- **購読の解除の仕方をアプリごとに。** 登録より詳しく書きます。Googleカレンダーは
  左の一覧から消すのと、設定から消すので結果が違います。iPhoneは「カレンダーを削除」が
  どこにあるか分かりにくい。**ここが不十分だと、やめたい人がやめられません**
- **反映は即時ではないこと。** 取りに来る間隔はアプリ側が決めます
- **中止・延期は取り消しとして届くこと。** ただし端末が同期しないと届かないこと
- **入らないもの。** MY予定、日程が未定・候補のままの予定、引き換え予定を決めていない特典チケット
- **これは非公式ツールであること。** 出典は必ず公式へ辿れるようにしてあること

置き場所は `public/timeline.html` の「カレンダーに追加する」シートからは分けます。
シートは操作するところで、読ませるところではありません。**別ページを立てて、シートからは
そこへ送ります。** 購読解除の説明は、登録したあとに探されるものなので、
フィードのURLを知っている人が辿り着ける場所に要ります。

### 段階

1. `public/assets/ics.js` を切り出し、`timeline.js` をそれに乗せ替える（見た目も出力も変えない）
2. `tools/build-ics-feed.js` で全部入りのフィードを生成する。墓標はまだ無し
3. 墓標（`STATUS:CANCELLED`、試合日+1週間）を足す
4. 説明ページを書き、`timeline.html` から導線を張る
5. 実機で確認する。Google / iPhone で、登録・更新の反映・取り消し・**解除**まで

## 公式サイトの利用条件

2026-08-27 に `robots.txt` と利用規約を確認した結果と、そこから決めた方針です。
原文は転載せず、要点と判断だけを残します。再確認が必要な場合は公式サイトを直接参照します。

### robots.txt

一般的なアクセスを禁止する `Disallow` はありません。禁止対象はSEO解析系のボット数種のみです。
`dotbot` に `Crawl-delay: 10` の指定があるため、**取得間隔は10秒以上空け、頻度は1日1回程度にとどめます。**

### 利用規約から決めたこと

| 規約の要点 | 設計上の対応 |
| --- | --- |
| 営業活動・営利を目的とする行為の禁止 | **アフィリエイトによる収益化を行わない。** ホテル提案も価格比較と導線提供にとどめる |
| 文書・画像・映像等の複製、他サイトへの転用（引用を含む）を控えるよう要請 | **記事本文とタイトルを保存も転載もしない。** 持つのは日時・対象・試合との対応という事実と、自分の言葉で書いたラベルだけ |
| V.I.（エンブレム、ロゴ、マスコット）および選手・監督等の肖像の使用制限 | **公式由来の画像を使わない** |
| リンクはトップページへ、という要請 | 要請であり禁止ではない。誤情報対策を優先し、**出典として記事URLへ直接リンクする**（後述） |
| 情報の正確性を保証せず、予告なく変更する旨の免責 | 免責事項を置き、「最終確認は公式サイトで」の導線を常設する |

販売開始時刻のような**事実そのものは著作物ではありません。**
保護されるのは記事の表現です。事実だけを持ち、表現を持ち込まない構造にすることで、この制約と両立させます。

### 出典表示についての判断

誤情報対策として全イベントに出典を持たせる方針と、トップページへリンクするよう求める規約の要請は衝突します。
検討した結果、**記事URLへ直接リンクします。**

判断の理由は次のとおりです。

- 規約の記述は「お願い致します」であり、禁止ではありません。
- このツールは日時という誤ると実害が出る情報を扱うため、**利用者がその場で一次情報を確認できることを優先します。**
- トップページへのリンクでは、該当記事に辿り着くまでの手間が大きく、確認の導線として機能しません。
- リンクは公式サイトへの送客であり、クラブの不利益にはなりません。

`source_url` に記事URLを保持し、公開画面では確認日とともにリンクとして表示します。
クラブから直接リンクを控えるよう求められた場合は、出典名と確認日のテキスト表示に切り替えます。

## 情報収集アーキテクチャ

万能スクレイパーを作りません。**一次情報源を優先し、記事は意味ラベルの直下だけを読みます。**

```text
一次情報源
   ├─ チケット販売スケジュール（常設・表形式）──┐
   ├─ 試合日程 matches.json ────────────┤
   └─ オンラインストアの商品ページ ───────┤
                                              ├─→ calendar-events.json
公式ニュース                                  │
   └─ /news 一覧の差分で新着検知              │
        └─ 意味ラベル直下だけを解析 ─────┤
             （取れないものは対象外にする）    │
                                              │
   手入力（自分が必要と判断したもの）─────┘
                                              │
        ┌─────────────────┬───────────────────┴──┐
        ↓                 ↓                      ↓
Supporter Timeline    ICSフィード          JSON Feed / RSS
```

**チケット販売は記事を解析しません。** 常設の販売スケジュールページに会員ランク別の販売日時が表形式であり、
Jリーグチケット側にも同じ情報があります。

**外部の応募フォームからは期限を取れません。** ログイン前は期間を表示しない、JavaScriptで描画される、
イベントページからホームへリダイレクトされる、といった理由によります。公式記事の「応募期限」行のほうが確実です。

公式サイトにRSS/Atomフィードはないため、新着検知はニュース一覧ページの差分で行います。
一覧には公開日、カテゴリ、記事リンクが出力されています。

取得は `robots.txt` の `Crawl-delay: 10` に合わせて10秒以上の間隔を空け、1日1回程度にとどめます。
ブラウザから直接取得できるか（CORS）は未確認のため、**GitHub Actions などで定期取得してJSONを生成し、
静的サイトへ反映する構成**を想定します。利用者向けのサーバーや認証は不要です。

取得できない状態が続く場合も、手入力だけでタイムラインは成立します。

出典と確認日は必ず残します。記事本文やタイトルは保存しません（「公式サイトの利用条件」参照）。

### 生成と検証の道具

CSVから `calendar-events` を組み立てるところまでは、リポジトリ内のツールにしました。
**手で組み立てると再現できず、CSVを取り直したときに作り直せないためです。**

| コマンド | 役割 |
| --- | --- |
| `npm run generate:timeline` | CSVと `matches.json` から `calendar-events` を生成する |
| `npm run check:timeline` | 生成物が最新かを突き合わせ（`--check`）、内容を検証する |

`tools/generate-calendar-events.js` が作るのは事実だけです。段階名は公式表記から自分の言葉のラベルへ
置き換え、記事本文やタイトルは持ちません。試合そのもののイベントは `matches.json` から作り、
日時の確からしさをそのまま写します。

`tools/validate-calendar-events.js` は次を見ます。

- 必須キーと語彙（`date_precision` / `type` / `action_type` / `source` / `status` / `ticket_kind`）
- `date_precision` と `starts_at` / `date_candidates` の組み合わせ
- `audience` のキーと会員種別コード
- `match_ids` が `matches.json` に存在すること
- 実データに `source_url` と `source_checked_at` があること（作り物の `is_sample` は対象外）
- **1試合のチケットイベントが8件そろっていること**（先行5段階＋特典チケット引換3件）
- `id` の重複、公開データに個人の予定が混ざっていないこと

検証を書いたことで、実データの性質が1つ分かりました。**候補日は1件のこともあります**
（第32節は4/29だけが挙がっていて未確定）。「候補は2件以上」という前提は成り立ちません。

HTMLからCSVを作る部分は「販売スケジュールの取得と解析」にまとめました。
残っているのは定期実行（1日1回）だけです。

### 販売スケジュールの取得と解析

公式のチケット販売スケジュール（常設・表形式）からCSVを作るところまでを、2つのコマンドに分けました。
**取得と解析を分けたのは、同じHTMLから何度でも同じCSVが出ることを、ネットワークなしで確かめられるようにするためです。**

| コマンド | 役割 |
| --- | --- |
| `npm run fetch:ticket-sales -- <出力.html>` | 公式ページを取得してHTMLを保存する |
| `npm run parse:ticket-sales -- <入力.html> <出力.csv>` | HTMLから販売スケジュールCSVを作る |
| `npm run check:ticket-sales` | 作り物の入力（`tools/fixtures/`）で解析結果が変わっていないか見る |
| `npm run check:ticket-sales:current` | 現在値のCSVから `calendar-events` を組み立てられるか見る |

出力の列構成は `docs/sheets/ticket-sales.2026-08-28.csv` と同じで、そのまま `npm run generate:timeline` に渡せます。

**現在値の正本は `docs/sheets/ticket-sales.current.csv` です。** 日付入りの
`ticket-sales.2026-08-28.csv` は当時の記録であり、書き換えません。プロトタイプの
`calendar-events.sample.json` は再現性のため日付入りのスナップショットに固定したままにしています。

**取得（`tools/fetch-ticket-sales.js`）** は「公式サイトの利用条件」に従います。素性の分かる User-Agent を送り、
前回の取得時刻を出力先の隣に記録して、既定では24時間以内の再取得を断ります（`--force` で上書きできます）。
失敗時の再試行は10秒（`Crawl-delay`）空けて最大3回です。

**解析（`tools/parse-ticket-sales.js`）** が読むのは次の4つの形です。公式ページは試合ごとに `dt`（見出し）と
`dd`（販売表）の対で並んでいます。

| 見出しの形 | 出力 |
| --- | --- |
| `<time datetime="...">8.22 (土) 19:00</time>` | `match_date` と `kickoff` |
| `2.13(土) or 2.14(日)` + キックオフ未定 | `match_date_candidates`（`\|` 区切り） |
| `日程未定` | 日付列は空 |
| 販売表なし | `schedule_status: 未掲載` と `schedule_note` |

**公式ページは年を書きません。** 見出しの `datetime` 属性がある試合はそこから取り、無い候補日と販売日程は
シーズン表記（`2026/27`）から補います。7月以降を開始年、6月以前を翌年とする規則で、2026-08-28の実データでは
候補日・販売日程ともこの規則と食い違いませんでした。読み取った日付が実在するかも確かめます。

**知らない段階名や表見出しが出てきたら失敗させます。** 黙って行が欠けるより、気付けるほうが安全なためです。

#### 1日1回の取り込み

`.github/workflows/ticket-sales-sync.yml` が毎日22:00 JSTに動き、
`docs/sheets/ticket-sales.current.csv` に差分があればdraft PRを作ります。手動実行もできます。
1回の実行で送るリクエストは1件だけです。

**取得日時と画面表示だけの違いでは更新しません。** `retrieved_at_jst` は取得のたびに動き、
`official_display_status`（`受付中` / `販売中`）は販売の開始・終了で日に何度も変わります。
どちらも販売スケジュールという事実ではないため、ここだけが違う場合は
`--keep-unchanged` でCSVを書き換えず、PRも作りません。**そうしないと、中身の変わらないPRが毎日立ちます。**

この扱いの結果、`retrieved_at_jst` は「最後に内容が変わった取得の日時」であって、
「最後に確認した日時」ではありません。毎日の確認結果はワークフローの実行履歴に残ります。

**内容が変わった回は、変わった値を言葉で挙げます。** `retrieved_at_jst` が全行で動くため、
生の差分では124行すべてが書き換わったように見えて何が変わったのか読めません。
パーサが移ろう列を除いて突き合わせ、`変更: 第3節 ... / sale_start: A → B` の形で並べたものを
PR本文と実行サマリーに載せます。

PRを作る前に `npm run check:static` を実行します。**GitHub Actions が作ったPRでは
ワークフローが起動しない**ため、Static Checksがこの自動PRに対して走らないためです。
公式ページの構成が変わったまま気付かずCSVを差し替えるのを避けます。

#### 実物のHTMLはリポジトリに置きません

「公式サイトの利用条件」の複製を控える方針に従い、取得したHTMLはコミットしません。
回帰確認に使うのは `tools/fixtures/ticket-sales.sample.html` で、これは構成だけを真似た作り物です
（シーズン・大会名・対戦相手・日付はすべて架空）。`npm run check:ticket-sales` がこの入力と
`tools/fixtures/ticket-sales.sample.csv` を突き合わせます。

#### 2026-08-28に確認したこと

公式HTMLを解析した結果は、19試合・124行で、`docs/sheets/ticket-sales.2026-08-28.csv` と
**124行中122行が完全に一致**しました。残る2行は解析の誤りではなく実データの変化です。
第7節ゴールドの販売開始が2026-08-28 12:00で、スナップショットは同日11:00の取得だったため、
`official_display_status` が空から `販売中` / `受付中` に変わっていました。
スナップショットは当時の記録として書き換えていません。

### チケット販売スケジュールのスナップショット

`docs/sheets/ticket-sales.2026-08-28.csv` は、公式のチケット販売スケジュール（常設・表形式）を
2026-08-28 11:00 に確認した時点の写しです。**現在値ではなくスナップショットです。** 保持しているのは
日時・対象・試合との対応という事実だけで、記事本文は含めません。

| 列 | 内容 |
| --- | --- |
| `season` / `competition` / `round` | シーズン、大会、節 |
| `match_date_raw` | 公式表記のままの試合日（`2.13(土) or 2.14(日)` を含む） |
| `match_date` / `match_date_candidates` | 確定日、または `|` 区切りの候補日 |
| `kickoff` / `opponent` | キックオフ時刻、対戦相手 |
| `entry_group` | `ticket_sale`（先行・一般販売）または `sc_benefit_exchange`（特典チケット引換） |
| `sale_type` | 公式表記の段階名 |
| `sale_start` | 販売・受付の開始日時（ISO 8601、`+09:00`） |
| `official_display_status` | 公式ページ上の状態表示（`受付中` / `販売中` / 空） |
| `schedule_status` | `掲載済み` / `未掲載` |
| `schedule_note` | 未掲載の理由 |
| `source_url` / `retrieved_at_jst` | 出典と取得日時 |

`entry_group` は `TimelineEvent` の `type` には対応しません。どちらも `type: "ticket"` として扱い、
`id` の接尾辞（`-gold` / `-benefit-gold`）と `title` で区別します。

`tools/parse-ticket-sales.js` はこの列構成で出力します（BOM付きUTF-8・CRLF）。

## AI利用方針

**AIによる抽出は使いません。** 調査の結果、決定的なパーサで足りることが分かったためです。
詳細は `docs/news-extraction-research.md` を参照してください。

### 調査で分かったこと

- 公式記事の本文には `応募期限`、`応募期間`、`申込締切`、`キャンペーン期間`、`購入受付期間`、`配布時間`、
  `対象試合` などの**意味ラベル**が見出しや表の行として存在します。
- 日時の書式は `YYYY年M月D日(曜)` / `M月D日(曜)` / `M/D(曜)` / `HH:MM` / `HH時MM分` / `～` / `本日` 程度に収まり、
  **文字列の抽出は正規表現で十分可能**です。
- 難しいのは日時を見つけることではなく、**その日時が何を意味し、どのイベントに属するかの判断**です。

### 方針

全文からの日時探索をやめ、**意味ラベルの直下だけを allow-list 方式で解析します。**
ラベルが示す意味（締切か、販売開始か、実施時刻か）をそのまま採用するため、意味づけの推論が不要になります。

相対時刻（「キックオフ1時間30分前」）は、`public/data/matches.json` の `kickoff_time` と結合して絶対時刻に直します。

### 取らないものを決める

次のいずれかに当てはまる記事からは、**日時を抽出しません。**

| 条件 | 理由 |
| --- | --- |
| タイムスケジュールが画像 | テキスト解析では原理的に取得できない |
| 変更履歴（「変更前」「変更後」、取り消し線）が含まれる | 素朴に拾うと古い日時を掴み、誤情報になる |
| 1記事に複数のイベントが含まれる | どの日時がどのイベントのものか対応付けられない |
| 日時に意味ラベルが付いていない | 締切か実施時刻かを判断できない |
| 日付を記事全体から推論する必要がある | 単独では日付が確定しない |

対象外にした記事はURLだけを一覧に残し、気になったときに自分で見に行けるようにします。

**「AIの誤りをすべて人間が確認する」のではなく、「機械が確実に取れるものだけ取り、取れないものは取らない」設計です。**
取らなかった情報は見逃しますが、それは元々ニュースを読んでいなければ見逃していた情報です。
誤った日時を出すよりも、出さないほうが安全です。

### AIを使う可能性が残る場所

対象外にした記事を扱いたくなった場合だけ、意味づけとイベント分割にAIを使う余地があります。
その場合も、画像のタイムスケジュールはAI以前にOCRが必要です。
処理はローカルまたは手元で実行し、GitHub Actionsの必須検証には載せません。
APIキーなどの認証情報はリポジトリに置きません（`AGENTS.md` の最重要ルール）。

## 変更検知

「8/22 → 8/30へ変更」を新規2件にしません。

```text
既存イベント          変更の通知             判定
柏戦 / 一般販売  →   柏戦 / 一般販売  →  既存Eventを更新
8/22 12:00           8/30 12:00
```

同一性の判定は、`id`（`種別-試合ID-識別子`）を安定キーとし、内容ハッシュを併用して差分を検出する方式を想定します。
「同一性キー＋内容ハッシュ」の考え方自体は本リポジトリ外の実装で用いた方式で、本リポジトリには該当コードはありません。
実装時は既存の `tools/asset-versions.mjs`（内容ハッシュで版数を決める仕組み）が参考になります。

### 記事の差分監視だけに頼らない

日時の変更は、記事側では既存記事の上書きとして反映されます。タイトルに「(8/25追記)」が付き、
本文には変更前の値が取り消し線で残ります。**素朴に日時を拾うと古い値を掴むため、
「変更履歴を含む記事は抽出しない」を対象外条件に入れています**（「AI利用方針」参照）。

一方、**ファンクラブ登録者へのメールでは、変更そのものが独立した1通として届きます。**
「■変更後の販売スケジュール」という見出しの下に、変更前と変更後が対比された形で書かれます。

したがって、**変更検知はメールを起点にするほうが確実です。** 日時変更のメールが届いたときに、
該当イベントを確認して更新する運用にします。メールは週2通程度であり、目視で足ります。

メールは個人宛の情報であるため、内容を公開JSONに含めません。あくまで運用者が気づくための手段です。
詳細は `docs/news-extraction-research.md` の「メール経路の調査」を参照してください。

## 運用者の作業

AI抽出をやめたことで、候補を承認・却下する管理画面は不要になりました。運用者の作業は次だけです。

- 取得スクリプトを実行し、`git diff` で `calendar-events.json` の差分を確認する。
- 手入力したいイベントがあれば直接書く。
- 公式メール（週2通程度）に目を通し、日時変更の通知があれば該当イベントを更新する。
- 検証（`tools/validate-calendar-events.js`）を通してコミットする。

**差分レビューがそのまま人間確認になります。** 既存のデータ更新運用（`docs/operation-flow.md`）と同じ形です。
専用の管理画面を作る必要が出るのは、AI抽出を再開する場合だけです。

公開後に誤りが判明したときのために、訂正の手順と見せ方（更新日時の表示、訂正の履歴）は決めておきます。

## 表示カテゴリ

ACTION と INFORMATION を分離します。

| 分類 | 例 |
| --- | --- |
| ACTION | チケット購入、応募、引換、並ぶ、移動する |
| INFORMATION | 開門、イベント開始、ウォームアップ、キックオフ |
| PERSONAL | 家を出る、食事、座席へ移動 |

トップ画面はACTIONを優先し、その下に全体タイムラインを表示します。
分類は色だけで表さず、ラベルまたはアイコンと併記します（`AGENTS.md` の実装上の保護事項）。

## 段階実装

**確実に取れるものから作ります。** 調査の結果、ニュース記事もAIなしで扱える範囲があると分かりました（`docs/news-extraction-research.md`）。

| Phase | 実装内容 | 完了条件の目安 |
| --- | --- | --- |
| Phase 1 | TimelineEventスキーマ / タイムラインUI / チケット販売スケジュールのParser / `matches.json` 連携 / LocalStorage MY予定 / **ICS出力** | `experiments/` のプロトタイプが実データで動き、`tools/validate-calendar-events.js` が通り、ICSがカレンダーアプリで購読できる |
| Phase 2 | ニュース一覧の新着検知 / 意味ラベルの allow-list パーサ / 相対時刻の解決 / プロフィール（会員種別）による並べ替え / 訂正の見せ方 | 対象外の記事を取り込まないこと、誤った日時を出さないこと |
| Phase 3 | PWA / イベント重複警告 / プロフィール（興味タグ） / JSON Feed | 出力が正本データと一致すること |
| Phase 4 | 「あなたの試合当日プラン」自動組み立て / 移動余裕時間の警告 / プロフィール（居住地・移動時間） | 当日の動線が1画面で組めること |
| 保留 | AI抽出 / 画像タイムスケジュールのOCR / 承認用の管理画面 | 対象外にした記事を扱いたくなった時点で再検討する |

ICS出力を Phase 1 に含めるのは、この段階にツール内の通知がなく、見に来るのを忘れると目的を達成できないためです。
通知はカレンダーアプリ側に任せます。

UIを伴う変更のため、Phase 1 は `docs/ui-prototype-workflow.md` に従い `experiments/supporter-timeline/` でのプロトタイプから始めます。
公開ページ化する段階で `docs/site-index.md`（入口ページ）と `docs/production-inventory-audit.md`（公開物一覧）を更新します。

さらに小さく始めるなら、Parserも作らず、手入力の `calendar-events.json` とタイムラインUIとICS出力だけで検証できます。
自動取得は後から足します。

## 出力先

タイムラインの正本はこのツールのデータで、外部サービスは出力先として扱います。候補は4系統あります。

### カレンダー系

| 方式 | 認証 | 静的ホスティングで可能 | 位置づけ |
| --- | --- | --- | --- |
| ICS購読フィード（`webcal://.../timeline.ics`） | 不要 | 可能 | 第一候補。一度登録すれば以後自動同期。Google / Apple / Outlook すべて対応 |
| ICS単発ダウンロード | 不要 | 可能 | 実装が最も軽い。**Android・iOSの両実機で、ダウンロードした `.ics` をカレンダーアプリが受け取れることを確認済み（2026-08-27）。** iOSは取り込み前に件数と一覧のプレビューを出す。ただし1回きりの取り込みで、自動同期はしない |
| Googleカレンダーのテンプレートリンク | 不要 | 可能 | クエリ文字列だけで「カレンダーに追加」ボタンが作れる |
| Google Calendar API連携 | OAuth必要 | 不可 | サーバーと認証情報が必要。現在の構成から外れる |

ICS購読フィードが用意できれば、Google Calendar API連携は不要になる可能性が高いと考えます。
API連携を検討するのは、ICSでは実現できない要件が出てからにします。

**購読フィードと単発ダウンロードは、どちらかを選ぶものではありません。** 前者は
「放っておいても最新」、後者は「今すぐ自分のぶんだけ」で、応える欲求が違います。
フィードは公開URLひとつなのでプロフィールによる絞り込みができず、MY予定も入れられません
（個人の予定を公開ファイルに入れない）。その2つは単発ダウンロードが担います。両方残します。

**どちらにも版が要ります。** `SEQUENCE` と `LAST-MODIFIED` を出さないと、
カレンダーアプリは同じ UID を見ても「更新」と判断できません。無い場合の挙動はアプリごとに
割れる（無視される／二重に入る）ため、当てにできない。UID 自体は
`ticket-{試合}-{販売段階}@sanga-timeline.invalid` と**中身に依存しない形**で作ってあるので、
識別の土台はすでにあります（`tools/generate-calendar-events.js`）。
版は前回の生成物と見比べ、カレンダーに出る項目が変わった予定だけ上げています
（2026-08-29に実装、2026-09-03に取得時刻ベースから変更）。取り直しただけで全予定の版が
上がると、フィードでは毎回全件が更新扱いになるためです。

**取り消しはフィードでしか解けません。** 販売が中止・延期になったとき、すでに利用者の
カレンダーに入った予定を、配ったファイルから取り消す手段はありません。フィードなら
`STATUS:CANCELLED` の項目として残すことで消せます。

### 通知系

| 方式 | 実現性 | 備考 |
| --- | --- | --- |
| カレンダーアプリの通知（ICS経由） | 可能 | 通知の仕組みを自前で持たずに済む。当面はこれを基本にする |
| Web Push（PWA） | 構成変更が必要 | 鍵と配信サーバーが要る。静的ホスティングから外れるため Phase 3 で判断する |
| ブラウザ内リマインド | 制約あり | 端末内で完結するが、ブラウザを閉じていると動かない場合がある |
| メッセージアプリ通知 | 要調査 | サーバーと各サービスの審査・仕様確認が必要。現時点では対象外 |

### 機械可読フィード系

- RSS / Atom / JSON Feed: 静的ファイルを置くだけで配信でき、利用者が自分の道具に繋げられる。
- `calendar-events.json` そのもの: 他ツール（Matchday Dashboard、年間スケジュールページ）から読む内部インターフェースでもある。

### 人間向け出力系

- SNS共有用の画像・テキスト（「今週やること」など）。既存の共有画像生成（`docs/screenshot-social-share.md`）を流用できる。
- 試合当日プランの印刷・スクショ用表示。既存のスクショ用表示と同じ考え方。
- ホーム画面ショートカットからの「次にやること」表示。

### 優先順位

1. **ICS出力（Phase 1 に含める）**
2. Googleカレンダーのテンプレートリンク（単発追加の導線）
3. JSON Feed / RSS
4. Web Push（構成変更の判断後）

ICS出力は Phase 1 に含めます。Phase 1〜2 にはツール内の通知がなく、利用者が見に来るのを忘れると
「販売開始を見逃さない」という目的を達成できないためです。通知はカレンダーアプリ側に任せることで、
通知の仕組みを自前で持たずに目的を満たせます。

これは元の企画方針（タイムラインを正本にし、カレンダーは出力先の一つ）の変更ではありません。
出力先の実現手段として、認証もサーバーも要らないICSを選んだというだけです。

### パーソナライズとの関係

**静的配信のICSフィードは全員に同じ内容を返すため、プロフィールを反映した個人別フィードは作れません。** 対応は次のいずれかです。

| 方法 | 内容 | 評価 |
| --- | --- | --- |
| 条件別に静的フィードを分ける | `timeline-diamond.ics` のようにグレード別へ分割 | サーバー不要。組み合わせが増えると破綻するため、軸は1つに絞る |
| 端末内でICSを生成してダウンロード | 絞り込み結果からその場で `.ics` を作る | 個人条件が外に出ない。ただし自動同期はできず、都度の書き出しになる |
| 個人別URLを発行する | 利用者ごとの購読URL | サーバーと状態管理が必要。現在の構成から外れる |

当面は「全体フィード＋端末内でのICS書き出し」を基本とし、グレード別フィードの分割は必要になってから判断します。

## ホテル提案との接続

リポジトリには、PR #122 で追加されたホテル候補データの生成基盤が残っています。

| 資産 | 状態 |
| --- | --- |
| `tools/hotels/`（楽天トラベルAPIクライアント、内部モデル、公開JSON変換、調査CLI、生成CLI） | 実装済み。ただし `build_match_hotels.py` は実APIを呼ばず固定のサンプルを返す足場 |
| `public/data/hotel-index.json` | 空索引（0件） |
| `public/data/hotels/{match_id}.json` | 未生成 |
| `tools/validate-hotels.js` | 稼働中。`npm run check:data` から常時実行される |
| `docs/hotels-data-schema.md` / `docs/hotels-operation-flow.md` | スキーマと運用手順を定義済み |

### 設計が一致している点

ホテル提案は、SUPPORTER TIMELINE と同じ構造で作られています。

- APIキーは `tools/` 側に閉じ込め、フロントエンドは `public/data/` の静的JSONを読むだけ。
- 索引ファイルと試合別詳細ファイルの2層に分け、必要な試合だけ遅延読み込みする。
- 試合との紐づけは `match_id`。

タイムライン側の `calendar-events.json` も同じ考え方で設計しているため、**データの作り方をそろえられます。**

### 出口としてのタイムライン

ホテル提案は現在、生成基盤だけがあって公開ページ側の出口がありません。
年間スケジュールページには 2026-07-09 に「日程表と直接関係しない情報を表示しない」方針でプレビュー枠を撤去した経緯があります。

**アウェイ遠征における「宿を取る」は、締切のある ACTION イベントです。** タイムラインなら日程表を邪魔せずに置けます。

- 遠征する試合を、プロフィールの `area`（居住エリア）と `match_ids` から判断する。
- 「宿を取る」を ACTION として、試合日から逆算した位置に置く。
- そのイベントから `public/data/hotels/{match_id}.json` を遅延読み込みして候補を見せる。

`docs/fan-tools-research.md` の AWAY PASSPORT や遠征支援系と同じ系統の機能でもあります。

### 再開するときに決めること

`docs/hotels-operation-flow.md` の「今後の実装ポイント」に加えて、次を確定してから実データを公開します。

- スタジアム座標と検索半径。
- 宿泊日ルール（前泊・後泊の判定をキックオフ時刻と居住エリアからどう決めるか）。
- 料金表示の鮮度（静的JSONに価格を含めると古くなる。価格を持たず導線だけにする案も含めて判断する）。
- **アフィリエイトによる収益化は行いません。** 公式サイトの利用規約が「営業活動または営利を目的とする行為」を
  禁止しており、抵触するおそれがあるためです。ホテル提案は価格比較と導線提供にとどめます。
- ダミーデータを公開対象に含めない手順（`build_match_hotels.py` 実行後の差分確認）。

現時点では、タイムラインのPhase 1〜2 にホテル提案を含めません。**先にタイムライン単体を成立させ、遠征イベントを扱えるようになってから接続を判断します。**

## 運用と公開の検討事項

設計が成立するかどうかは、実装できるかよりも「続けられるか」「信じてもらえるか」で決まります。
着手前に方針を決めておくべき点を、リスクの大きい順に挙げます。

### 1. 運用が一人で回るか（設計で回避）

当初は「AIが抽出し、誤りを人間がすべて確認する」設計だったため、確認作業が止まればツールの情報が古くなる
弱点がありました。

調査の結果、**確認そのものを不要にする方針に変えました。** 機械が確実に取れるものだけを取り、
取れないものは抽出せず対象外にします。運用者の作業は `git diff` での差分確認だけです。

**取りこぼしは残ります。** 対象外にした記事の情報は扱えません。ただしそれは、元々ニュースを読んでいなければ
見逃していた情報です。**負荷の先送りではなく、扱う範囲を明示的に狭めた**という点が以前と違います。

「他人のための情報収集を一人で背負う」構図にならないよう、まず自分が使うツールとして成立させ、公開はその副産物とします。

対象外にした記事を扱いたくなったときは、着手前に週あたりの件数と1件あたりの所要時間を実測してから判断します。

### 2. 通知がない段階で価値が出るか（対応済み）

**ICS出力を Phase 1 に含めることで対応します。** 利用者はカレンダーアプリで購読でき、通知もそちらに任せられます。
ツールを見に来るのを忘れても、目的である「販売開始を見逃さない」は達成されます。

### 3. 誤情報の責任と訂正

日時を扱うツールは、間違えると「買い逃した」という実害につながります。年間スケジュールページより強い扱いが必要です。

- **全イベントに出典URLを表示する。** 出典のないイベントは公開しない。確認日も併記する。
- 最終確認は公式サイトで行うよう促す導線を常設する。
- 公開後に誤りが判明したときの訂正手順と、訂正をどう見せるか（更新日時、訂正の履歴）を決めておく。
- 免責事項を置く。年間スケジュールページの既存実装に合わせる。

### 4. 情報の書き方と権利

日時そのものは事実ですが、**公式記事のタイトルや本文をそのまま転載すると別の問題になります。**

- イベント名は自分の言葉で書く。記事本文とタイトルは保存も転載もしない。
- 画像は使わない。公式サイトのV.I.（エンブレム、ロゴ、マスコット）と選手等の肖像は利用が制限されている。
- 詳細は「公式サイトの利用条件」節を正とする。

### 5. 過去イベントと初期表示

タイムラインは放置すると過去のイベントで埋まります。

- 終わったイベントを消すか、畳むか、薄く残すか。
- 画面を開いた瞬間、どこにスクロールしているか（「今」の位置）。
- シーズン終盤に件数が増えたときの初期読み込み範囲とデータ分割。

地味ですが、毎回の使い勝手を直接左右します。プロトタイプで実データを入れて確認します。

### 6. 年間スケジュールページとの導線

役割は分けましたが、**利用者はどちらを開けばよいか迷います。**

- 試合カードから、その試合に関するタイムラインへ移動できるようにする。
- タイムラインの試合イベントから、試合カードへ戻れるようにする。
- 入口ページ（`docs/site-index.md`）の説明文を、2つのツールで書き分ける。

### 7. 公開の形とスコープ外

- 公開パス（`public/timeline.html` など）、`docs/site-index.md` への追加、OGP、メタ情報。
- 本番反映は `docs/deploy-policy.md` と `docs/operation-flow.md` に従う。
- **やらないことを明示する。** 順位表、移籍情報、リアルタイム速報、選手個人の動向は対象外とします。
  スコープ外を書いておかないと、要望のたびに範囲が広がります。

## 成功条件

- 販売開始を見逃しにくい。
- 1画面で直近行動がわかる。
- 別試合の予定も混在表示できる。
- 試合当日の動線を組みやすい。
- 公式記事を何本も開かなくてよい。
- AI誤抽出がそのまま公開されない。
- 自分に該当する先行販売が、自分で調べなくても分かる。
- プロフィール未設定でも使える。

設計上の最重要ポイントは、「AIで公式情報を完璧に全部拾う」ことを成功条件にしないことです。
まず安定して取得できる構造化情報から始め、ニュースは候補抽出＋人間確認で段階的に広げます。
これにより、情報収集精度が100%でなくてもツール全体が成立します。
