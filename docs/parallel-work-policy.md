# 複数実装者の並行作業と検証の指針

記録日: 2026-08-21

## 目的

複数の実装者（人間・AIを問わず）が同時に別PRを進めたときに起きた手戻りを整理し、次回同じ形で作業しても同じ問題が起きないようにするための指針です。

この文書は運用手順の一部です。実装ルールそのものは `AGENTS.md` と `docs/codex-workflow.md`、文書の更新条件は `docs/documentation-policy.md` を正とします。

## この指針のもとになった作業

2026-08-21に、次の3系統が並行しました。

| PR | 内容 | 種別 |
| --- | --- | --- |
| #154 | 予想スカッドにスタイル「シンプル」を追加 | 実装（`public/`） |
| #155 / #156 | 現行仕様の同期、アーカイブ整理 | 文書 |
| #157 | 出典・ライセンスの棚卸し | 文書 |
| #158 | スカッドの本番デプロイ前検証を追加 | CI＋実装 |
| #159 / #160 | 上記の相互追従 | 文書 |

結果として、追従だけのPRが2本増えました。以下はその原因と対策です。

## 並行作業のルール

### 1. 触るファイルを先に宣言する

実装PRと文書PRが同時に走ると、文書PRが実装PRの結果を知らないままマージされます。今回は #155 / #156 が「7スタイル」の記述でマージされ、#154 のマージ直後に古くなりました（#159 で追従）。

- 作業開始時に、変更予定のファイルをPR本文かIssueに書く。
- 重複した場合は、片方を先にマージし、もう片方が最新 `main` を取り込んでから続ける。
- 実装PRと、その実装を説明する文書PRを同時に走らせない。どうしても分ける場合は、実装PRのマージ後に文書PRを更新する前提で進める。

### 2. 件数・一覧は正本を1か所にする

同じ数値が複数の文書に散ると、追従漏れがそのまま残ります。今回は「スタイル7種類」が `docs/roadmap.md` と `docs/ai/SQUAD_BROWSER_CHECKLIST.md` の2か所にありました。

- 数値や一覧は、可能なかぎり自動検証で担保する（例: `tools/validate-squad-contract.mjs` はスタイルの並び順・フォーメーション件数・選手件数を実データと突き合わせる）。
- 文書に書く場合は、確認日と確認方法（実行したコマンド）を併記する。

## 自動検証の作り方

### 3. 検証は「情報量が最大の状態」を必ず含める

自動レイアウト検証を追加した時点（#158の初版）では、ピッチの11枠を空のまま全1,632通りを検証していました。空スロットでは日本語名が表示されないため、**選手を配置したときにだけ起きる重なりを検出できませんでした**。実際、11人配置で計測すると、シンプルは51通り中18通りで円とポジション名が重なっていました。

- 表示物が入力状態で増減する画面では、「すべて埋まった状態」を必ず検証対象に含める。予想スカッドなら、スタメン11人・控え最大・タイトル・試合情報・投稿者名まで入力した状態。
- 空・最小の状態も別途検証する。両方が必要で、どちらか一方では足りない。
- 検証を追加するPRでは、「その検証が実際に落ちること」を先に確認する（既知の不具合を入れて赤にしてみる）。

### 4. レイアウト計算は固定値ではなくDOMの実測から導く

シンプルはカードの外に名前を出すため、占有高さが「カード＋ポジション名」ではなくなりました。当初はこの差分を計算に入れておらず、縦間隔を過小評価していました。

- 占有領域は、代表要素の `getBoundingClientRect()` からカード高さに対する比率として求め、スタイルごとの分岐を増やさない。
- スタイル固有の値を計算式に直接書かない。書く場合は、CSS側の該当箇所へ相互にコメントで参照を張る。

## 実装の確認方法

### 5. CSSは失敗しても例外を出さない。数値で確かめる

背番号タイルの中央寄せ補正は、CSS変数に単位付きの値（`--tile-dx:-1.7%`）を渡していたため `calc(var(--tile-dx) * 1%)` が無効値になり、**補正がまったく効いていない状態で「効いている」と報告していました**。見た目の印象では気づけませんでした。

- 位置・寸法の調整は、描画後の値を計測して検証する（要素の矩形、`getComputedStyle` の `transform` など）。
- CSS変数を `calc()` へ渡すときは単位なしの数値にし、単位はCSS側で掛ける。
- 「直したはず」で終わらせず、修正前後の数値を残す。

### 6. 画像アセットのばらつきは測って持たせ、生成手順を同梱する

背番号タイルは画像ごとに中身が左右±6%・上下±4%ずれていました。個別のCSSを書かず、測定値を生成物として持たせています。

- 生成物（`public/assets/squad-tile-offsets.js`）と生成ツール（`tools/measure-tile-offsets.mjs`）を対にする。
- 生成物の先頭に「自動生成」と再生成条件を書く。
- 素材を差し替えるPRでは、再生成したかどうかをPR本文に書く。

## デプロイ前検証

### 7. デプロイ経路に重い検証を足すときは所要時間を記録する

本番デプロイは、確認入力と `main` 限定の判定のあとにスカッド事前検証を通す構成になりました。ブラウザ検証を含むため、デプロイ経路がネットワークとブラウザ導入に依存します。

- 追加した検証の実測時間をPR本文と手順書に残す（2026-08-21時点で1分35秒／タイムアウト15分）。
- 所要時間がタイムアウトに近づいたら、デプロイ経路と日常のPR検証に分ける。

## 統合・引き継ぎ・デプロイの追加ルール

### 8. 統合担当とマージ順を決める

複数PRが同じ文書や実装へ影響する場合、各PRが個別に正しくても、マージ順によって後続PRの前提が古くなります。今回は #157 を先にマージし、#158を最新 `main` へ載せ直してから再検証する統合作業が必要でした。

- 並行作業の開始時に、依存関係、想定マージ順、最後に整合性を確認する統合担当を決める。
- 引き継ぎ時は、ブランチ名、base/head SHA、変更ファイル、CI実行URL、未対応事項を残す。
- 後からマージするPRは、作業再開前とマージ直前に最新 `main` との差分を確認し、`behind 0` にする。
- 同じブランチを複数の実装者が同時更新しない。更新者を交代するときは、前の実装者が停止したことと最新head SHAを確認する。
- 重複ファイルは片方の内容で上書きせず、先にマージされた変更を保持した上で後続PRの差分を統合する。

### 9. 必須セレクタと参照は「0件」を成功にしない

#158の初版では、DOMに存在しない `.name-en` を検証対象へ含めていました。セレクタが0件でもループ自体は成功するため、検証しているつもりで何も確認していない状態になります。

- 必須セレクタは、重なりや寸法の判定前に一致件数が1件以上であることを検証する。
- 0件を許すセレクタは任意項目として明示し、許す理由を書く。
- 必須ファイルは存在確認だけで終わらせず、HTMLやJavaScriptから実際に参照・importされていることまで確認する。
- 公開CSS/JavaScriptを変更する場合は、HTMLのキャッシュ用バージョンクエリも契約検証へ含める。
- 新しい検証は、既知の不具合や意図的な欠落で一度失敗させ、検出能力を確認する。

### 10. PR検証とデプロイ前検証の実行範囲を分ける

全1,632組み合わせのChromium検証は本番デプロイ前の安全網として有効ですが、文書だけのPRでも毎回実行すると、レビューの待ち時間とActionsの実行量が増えます。#160のような `docs/` だけの変更でも同じブラウザ検証が走りました。

- 本番デプロイ前は、変更ファイルに関係なくスカッドの完全検証を実行する。
- PRでは、スカッドのHTML/CSS/JavaScript、選手データ、配置計算、検証ツール、関連Workflowを変更した場合に完全検証を実行する。
- 文書だけのPRは軽量な静的検証を基本とし、完全検証を省略した場合もPR本文に理由を残す。
- パス条件を導入するときは、検証コード自身の変更を除外しない。
- タイムアウトまでの余裕だけでなく、通常PRのフィードバック時間と実行頻度も継続的に確認する。

2026-08-25に `.github/workflows/static-checks.yml` へ判定を実装した。`docs/` 配下・
リポジトリ直下のMarkdown・`LICENSE` **だけ**の変更なら、スカッド事前検証を省略する。

許可リスト（「このファイルが変わったら検証する」）ではなく、除外リスト
（「文書だと分かるものだけ省略する」）にしている。許可リスト方式では、
新しく増えたファイルが条件から漏れたまま検証されずに通ってしまうため。
比較元をたどれない場合も、判定せず検証する側へ倒す。

本番デプロイ（`deploy-production.yml`）はこの判定を通さず、変更内容にかかわらず
必ずスカッド事前検証を実行する。

### 11. デプロイの実行者・監視者・完了条件を分ける

GitHub Actionsの手動実行には、Workflowを起動できる権限とログイン済み環境が必要です。実行権限を持たない実装者が無理に代行せず、リポジトリ所有者が起動し、別の実装者が実行URLを受け取って監視する分担を許容します。

- 実行前に、対象が `main` であること、対象commit SHA、直前の本番ファイルのバックアップ完了、公開範囲が `public/` だけであることを確認する。
- 現行Workflowは本番ファイルのバックアップを自動作成しないため、起動前に実行者が別途バックアップを確認する。
- 起動後は実行URLを共有し、確認入力、スカッド事前検証、日程JSON・JavaScript検証、FTPアップロードを順に監視する。
- 完了後はWorkflowの成功だけでなく、本番URL、利用者向けの変更、CSS/JavaScriptのバージョンクエリ、ページ由来のエラーを確認する。
- 更新告知は、本番URLで期待した変更を確認してから行う。
