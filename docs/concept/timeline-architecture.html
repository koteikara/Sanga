SANGA SUPPORTER TIMELINE

公式情報を、サポーター本人の時間軸に統合する。設計上の判断が実際にどう噛み合うかを5枚の図にした。

設計基準日 2026-08-27 ／ 正本 docs/supporter-timeline-design.md
01

全体の流れ

正本は calendar-events.json ひとつ。外部サービスはすべて出力先として扱う。情報源の性質ごとに、通る経路が違うのがこの図の要点になる。

02

記事1本をどう扱うか

ここがAI抽出を置き換えた仕組みになる。全文から日時を探すのをやめ、意味ラベルの直下だけを読む。ラベルが「応募期限」と言っているなら、それは応募期限である。意味を推論する必要がない。

03

変更をどこで捕まえるか

販売日時の変更は実際に起きる。同じ変更が、記事とメールでまったく違う形で届くことが分かった。

04

確定していない日時をどう出すか

試合57件のうち28件が未確定、18件は候補日が複数、19件は日付そのものが未定。未定は例外ではなく、およそ半分を占める。

05

属人的な条件をどこで突き合わせるか

先行販売の開始日時は会員種別で違う。「自分の販売はいつか」を出すには属性が要るが、属性をサーバーに置く必要はない。

06

まだ決まっていないこと

  • ニュース記事の実件数。調査で月40件と月96件という2倍以上の開きがあり、対象外に落ちる記事の実数が変わる
  • ブラウザから公式サイトを直接取得できるか。取得は GitHub Actions を前提にしているが未確認
  • 公開データのファイル名。calendar-events.json は第一候補にすぎない
  • ICSフィードを条件別に分けるか、端末内での書き出しにとどめるか
  • 先行販売の順序と、会員種別ごとに販売日時が何本になるか
