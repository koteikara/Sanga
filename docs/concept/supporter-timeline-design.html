SANGA TOOLBOX / CONCEPT DESIGN

SANGA SUPPORTER TIMELINE

京都サンガF.C.の公式情報に散在する「チケット販売」「応募締切」「試合日イベント」「開門」「キックオフ」などを、サポーター本人の時間軸に統合し、次に何をすべきか・当日どう動くかを一画面で追える非公式ファンツール。

01 / 解決したい課題

公式情報が「時系列」でつながっていない

  • チケット販売開始が別ページ・別記事
  • イベント開始時刻が試合ニュースの中に埋まる
  • 応募締切・引換開始・グッズ販売なども別管理
  • 試合当日の「どの順で動くか」は自分で組み立てる必要がある
  • 結果として「販売開始を忘れた」「イベントが重なった」「座席に戻る時間が足りない」が起きる
02 / 設計原則

主役は「試合」ではなく「サポーター本人」

すべての情報を、試合単位ではなく1本のサポータータイムラインに並べる。

ALL チケット 応募 試合当日 MY予定

各イベントに matchIds を持たせ、必要なときだけ特定試合へ絞り込む。

04 / 情報モデル

TimelineEvent を最小単位にする

{
  "id": "ticket-kashiwa-general",
  "datetime": "2026-08-30T12:00:00+09:00",
  "type": "ticket",
  "title": "一般販売開始",
  "source": "official",
  "actionType": "action",
  "matchIds": ["2026-j1-kashiwa-home"],
  "sourceUrl": "...",
  "status": "confirmed"
}

matchIds は0件・1件・複数件を許可。クラブ全体イベントにも対応する。

05 / MY予定

公式予定と自分の予定を同じモデルで扱う

{
  "id": "my-seat-20260830",
  "datetime": "2026-08-30T18:10:00+09:00",
  "type": "personal",
  "title": "座席へ移動",
  "source": "personal",
  "matchIds": ["2026-j1-mito-home"]
}

UI上では同じ時系列に並ぶため、公式情報と自分の行動計画が自然につながる。

07 / AI利用方針

ローカルLLM中心でコストを抑える

段階処理AI
1構造化ページ使わない
2記事本文抽出使わない
3日時候補抽出正規表現中心
4意味付け・JSON化Qwen 7B/14B
5難解記事クラウドLLMへフォールバック

クラウドLLMは全記事ではなく、低confidenceや訂正記事など一部だけ。

08 / Qwenに任せること

「抽出」より「意味付け」をさせる

  • この日時は販売開始か、締切か
  • どの試合に関係するか
  • 新規イベントか、既存イベントの変更か
  • 複数イベントを分割する
  • JSONスキーマに整形する
推奨：まずQwen 7Bと14Bで30〜50記事を比較し、日時Recall・変更判定・誤イベント生成・JSON安定性を評価する。

14 / 成功条件

便利さの判定基準

  • 販売開始を見逃しにくい
  • 1画面で直近行動がわかる
  • 別試合の予定も混在表示できる
  • 試合当日の動線を組みやすい
  • 公式記事を何本も開かなくてよい
  • AI誤抽出がそのまま公開されない
設計上の最重要ポイント： 「AIで公式情報を完璧に全部拾う」ことを成功条件にしない。まず安定して取得できる構造化情報から始め、ニュースは候補抽出＋人間確認で段階的に広げる。これにより、情報収集精度が100%でなくてもツール全体が成立する。
