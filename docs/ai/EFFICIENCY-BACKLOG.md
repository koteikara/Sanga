# AI作業効率の改善バックログ

状態: 進行中（2026-08-25 起票）

AIエージェントがこのリポジトリで作業するときの、読み込みトークン量と手戻りを減らすための課題一覧です。
「毎回必ず発生するコスト」を減らすことを目的とし、機能追加は扱いません。

## 前提として測った規模

| 対象 | 規模 |
| --- | --- |
| 実装コード（HTML・JS・CSS） | 約5,900行 |
| `docs/*.md`（現行文書のみ、直下） | 約5,900行 |
| `docs/ai/` | 約520行 |
| `docs/` 全体 | 約1.4MB |

実装量と現行文書量がほぼ同じです。文書が増えるほど、変更1件あたりの読み込みコストが上がります。

## 対応済み

### 1. 検証コマンドを1コマンドへ集約（完了）

`package.json` に `npm run check` 系を用意し、`AGENTS.md`、`README.md`、`docs/project-structure.md`、
`docs/codex-workflow.md`、3つのワークフローYAMLがすべて同じスクリプトを参照するようにしました。
CIのステップ内に直書きしていたCSS波括弧数チェックとHTML参照チェックは
`tools/check-static-assets.mjs` へ移し、手元でも同じ検証が動きます。

効果: 必読文書からコマンド羅列が消える、実行漏れが起きない、CIと手元の定義が一本化される。

### 2. `docs/archive/` を調査対象から外す明示（完了）

`AGENTS.md` の必読文書節に、`docs/archive/` は現行仕様ではなく検索対象から外す旨を明記しました。
`docs/archive/ai/WORKLOG-2026-06-22_to_2026-07-09.md` は単体で2,178行あり、全文検索すると
現行仕様と過去記録が区別なくヒットします。

## 未対応

### 3. `docs/ai/JS_CHANGE_CHECKLIST.md` の圧縮とスクリプト移管

現状199行あり、JavaScriptを変更するたびに読み込み対象になります。長すぎて実際に守られたかの検証もできません。

- 各項目を「スクリプトで検証できる」「人間の目視でしか確認できない」に二分する。
- 前者は `tools/validate-app-contract.js` / `tools/validate-squad-contract.mjs` へ移し、文書からは削る。
- 後者だけを残せば、チェックリストは大幅に短くなり、かつ「読めば守れる」内容になる。

判断基準: 自動検証に落ちた項目を文書に残さない。二重管理は必ずずれる。

### 4. `*-inventory.md` の自動生成化または廃止

`docs/js-inventory.md` は431行で、対象の `public/assets/app.js` は953行です。
インベントリを読むより実物を `grep` するほうが速く、かつ実装とずれない状態になっています。
`docs/css-inventory.md`（348行）、`docs/html-analysis.md`（265行）も同様です。

- 実装から自動生成する（`tools/` に生成スクリプトを置き、CIで差分を検出する）か、
- 廃止して「該当箇所の探し方」を数行で示す形へ置き換える。

手書きインベントリは、実装とずれたときに誤った前提を高いトークンコストで刷り込むため、
放置コストが単なる無駄より大きい点に注意します。

### 5. `AGENTS.md` の必読表を索引方式へ

現状はUI変更1件でも `html-analysis.md` + `css-inventory.md` + `js-inventory.md` + チェックリスト2本で
1,200行超を読む設計です。各文書の冒頭に10行程度の「この文書の索引」を置き、
全文読解は必要なときだけにします。課題4と合わせて進めるのが効率的です。

### 6. ブランチとPRの1対1化

`claude/squad-tool-simple-style-1fobyq` のように、同一ブランチで複数PR（#167〜#169）を出した履歴があります。
「変更を小さく分ける」方針自体は妥当ですが、ブランチ名を再利用するとPRとブランチの対応が崩れ、
後から履歴をたどるコストが上がります。1PR = 1ブランチに揃えます。
`docs/parallel-work-policy.md` に追記するのが適切です。

## 進め方

課題3・4・5は相互に関連するため、4→5→3の順で進めると重複作業が減ります。
いずれも実装の挙動を変えないため、文書のみのPRとして分割できます。
