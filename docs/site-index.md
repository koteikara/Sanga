## 目的と現状の問題

`public/index.html` は本番サーバーの `/` にあたる公開サイトの入口です。ところが現状は次の状態にあります。

```html
<title>京都サンガF.C. 年間スケジュール確認環境</title>
<p>GitHub Pagesで公開する本番反映前の確認用トップページです。</p>
```

訪問者が最初に見るページが「本番反映前の確認用」と自己紹介しています。GitHub Pagesを確認環境として使う方針は変わりませんが、`index.html` 自体は本番の入口であり、記述が実態と食い違っています。

導線も不足しています。公開しているページは5件ですが、`index.html` から辿れるのは2件だけで、求・譲ツール、スライド、2025シーズン日程は直URLでしか到達できません（`docs/production-inventory-audit.md`）。

この設計は、`index.html` を「各ツールへの入口」として作り直すためのものです。

## 位置づけ

* `public/index.html` は公開サイトの入口として、各ツールへの導線を提供する。
* GitHub Pagesは引き続き本番反映前の確認環境として使う。入口ページもそこで確認する。
* 検証用プロトタイプへは導線を作らない（`docs/roadmap.md` の開発方針）。
* 非公式のファン作成物であることを入口で明示する。既存ページと同じ趣旨の表記を置く。

## 情報構造

区分は3つです。訪問者が「今使うもの」と「過去のもの」を取り違えないことを優先します。

| 区分 | 内容 | 掲載するもの |
| --- | --- | --- |
| 主要ツール | 現在も更新しているツール | 年間スケジュール、予想スカッド |
| 補助ツール | 現役だが用途が限定的 | 求・譲 投稿フォーマット生成 |
| 過去のページ | 更新していないが残しているもの | 2025シーズン日程、選手が思う"サンガのみりょく" |

過去のページを載せるのは、直URLで共有されている利用者が戻ってこられるようにするためです。更新していないことが分かる見せ方にし、主要ツールと同じ扱いにはしません。

将来ツールが増えた場合（`docs/service-scope.md` のニュース連動カレンダーなど）は、同じ区分のどれかに追加します。区分自体を増やす場合はこの文書を更新します。

## `tools.json` のスキーマ

入口ページに載せるツールは `public/data/tools.json` で管理します。ツールの追加・削除・文言変更をHTMLの編集なしで行えるようにするためです。

### 項目

| キー | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `id` | 文字列 | 必須 | ツールの識別子。英小文字とハイフン。一意 |
| `name` | 文字列 | 必須 | 入口ページに出す名前。ページの `<title>` と揃える必要はなく、一覧で分かりやすい表記にする |
| `description` | 文字列 | 必須 | 1文の説明。何ができるページかを書く |
| `href` | 文字列 | 必須 | `public/` からの相対パス。同一サイト内のみ。外部URLは扱わない |
| `section` | 文字列 | 必須 | `primary` / `secondary` / `archive` のいずれか。上記の3区分に対応する |
| `updatedNote` | 文字列 | 任意 | 「2025シーズンの記録」のような補足。`archive` では原則書く |

### JSONの形

```json
{
  "updatedAt": "2026-08-26",
  "tools": [
    {
      "id": "season-schedule",
      "name": "年間スケジュール",
      "description": "2026/27シーズンの試合日程を確認し、参戦予定を保存できます。",
      "href": "sanga202627season.html",
      "section": "primary"
    }
  ]
}
```

### 決めたこと

* 掲載順は配列の順序に従う。並べ替え用の項目は持たない。順序を変えたいときは配列を並べ替える。
* `section` は固定の3値にする。自由な文字列にすると表示側が壊れるため、検証で弾く。
* 画像・アイコンは持たない。入口ページで画像を使うかどうかは見た目の設計で決めるため、決まってから項目を足す。
* 個人メモ、運用者メモ、認証情報は含めない（`AGENTS.md`）。

## 描画方式とJavaScript無効時の扱い

`tools.json` を読み、カードを組み立てて表示します。データ変更だけでツールを追加できる形にするためです。

一方で入口ページは、訪問者が最初に開くページです。JavaScriptが動かない環境で真っ白になるのは避けます。次の形にします。

* `index.html` に `<noscript>` を置き、主要ツールへのリンクを素のHTMLで書く。
* JavaScriptが動く場合は `tools.json` から全区分を描画する。
* `tools.json` の読み込みに失敗した場合も、`<noscript>` と同じ内容を表示に残す。読み込み失敗で導線が消えないようにする。

`<noscript>` に書くリンクは主要ツールのみとし、`tools.json` との二重管理を最小にします。この重複は検証で突き合わせます（後述）。

読み込みパスは既存ページと同じく、絶対パスと相対パスの順で試します。本番サーバーとGitHub Pagesでルートが異なるためです（`public/assets/squad-builder.js` と同じ方式）。バージョンクエリも既存ページに合わせて付けます。

## ページ共通のメタ情報

現状は `TradePost/index-v1.html` に `description`、`squad.html` に favicon があるだけで、OGPはどのページにもありません。SNSで共有されたときの見え方が揃わないため、全公開ページで揃えます。

| 項目 | 方針 |
| --- | --- |
| `description` | 全ページに置く。そのページで何ができるかを1文で書く。入口ページの `tools.json` の `description` と揃える |
| favicon | `squad.html` にあるSVGデータURIを全ページで共有する。外部ファイルにはせず、現状の方式を踏襲する |
| `og:title` / `og:description` | 各ページの `<title>` と `description` に合わせる |
| `og:type` | `website` |
| `og:url` | 本番の公開URL |
| `og:image` | 今回は入れない。共有用画像は日程・スカッドが生成する仕組みを持っており、静的なOGP画像の要否は別途判断する |

`og:image` を省くと、SNSでの見え方は文字情報だけになります。画像を用意するかどうかは、見た目の設計と合わせて決めます。

## 検証

`npm run check:static` から実行します。検証コマンドは `package.json` に集約し、ワークフローYAMLへ直接書きません（`AGENTS.md`）。

`tools/validate-tools.js`（新規）で次を確認します。

* `id` が一意で、英小文字とハイフンのみ。
* `section` が `primary` / `secondary` / `archive` のいずれか。
* `href` が `public/` 配下に実在する。**リンク切れをここで落とします。** ページを削除・改名したときに入口が壊れたまま気づかない事態を防ぐのが主目的です。
* `href` が外部URLでない。
* `name`、`description` が空でない。

`tools/check-static-assets.mjs` に次を追加します。

* `index.html` が `tools.json` と入口用JavaScriptを参照していること。
* `<noscript>` 内のリンク先が、`tools.json` の `primary` の `href` と一致すること。二重管理のずれを検出します。

## 実装の段取り

見た目を伴う変更のため、`docs/ui-prototype-workflow.md` に従いプロトタイプを先に作ります。

1. **見た目の設計**（別途）。配色は日程ページの紫系とスカッドの緑系に割れているため、入口ページをどちらに寄せるか、または中立にするかを決める。カード、区分の見せ方、過去ページの扱いを含む。
2. **プロトタイプ**を `experiments/site-index/` に作り、GitHub Pagesで確認する。
3. **`tools.json` と検証**を先に入れる。データと検証だけなら見た目の決定を待たずに進められる。
4. **本番実装**。`public/index.html` の書き換え、入口用CSS/JavaScriptの追加。
5. **メタ情報の統一**を全公開ページへ適用する。
6. 本番反映は `docs/deploy-policy.md` の手順に従う。

3と5は見た目の決定に依存しないため、1・2と並行して進められます。

## この設計で決めていないこと

* 入口ページの配色、レイアウト、カードの見た目。
* 画像・アイコンを使うかどうか。使う場合の `tools.json` の項目追加。
* OGP画像を用意するかどうか。
* `TradePost/` に `index.html` が無く `/TradePost/` で到達できない問題（`docs/production-inventory-audit.md` の未解決課題）。入口から `index-v1.html` へ直接リンクすれば導線は成立しますが、URLの見た目としては整えたいところです。
