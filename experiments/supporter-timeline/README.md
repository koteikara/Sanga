| 段階 | 時刻 | `audience` |
| --- | --- | --- |
| シーズンパス先行受付 | 11:00 | `{"season_ticket": true}` |
| プラチナ先行販売 / 特典チケット引換 | 12:00 | `{"fc_grade": ["platinum"]}` |

**販売日時は時間が経つと過去になる。** 「次にやること」が空になった場合は、
より先の試合をCSVから足すか、スナップショットを取り直す。

`skipped` は「取り込まなかった記事」を表す。設計上、機械的に確実に読めなかった記事は日時を抽出せず、

現在の5件は作り物のサンプル。

| --- | --- | --- |
| `sanga-timeline-personal-events-v1` | TimelineEventの配列 | MY予定 |
| `sanga-timeline-profile-v1` | `{ fc_grade, has_season_ticket, updated_at }` | サポータープロフィール |

プロフィールは端末内だけで扱う。照合もサーバーへ送らずに画面側で行うため、個人の属性はどこにも記録されない。
`fc_grade` は `platinum` / `gold` / `regular` / `kids` / `none` と未設定（空文字）のみを保存し、
知らない値が入っていた場合は未設定として扱う。「保存した設定を削除する」で消せるのはプロフィールだけで、MY予定は消さない。

**既存の `sanga-schedule-*` キーには触れない。** 年間スケジュールページの状態を壊さないため。
公開JSONにも個人の予定は含めない。

## ICSについて

書き出すのは `date_precision` が `datetime` または `date` のものだけ。
`candidates`（候補日が複数）と `unknown`（日程未定）は含めない。

購読カレンダーに入った予定は利用者にとって確定情報として届くため、候補日を流すと誤情報になる。
確定した時点でフィードに現れるほうが信用できる、という判断による。

書き出したファイルは `sanga-timeline-sample.ics`。カレンダーアプリで開いて、
日時と件数が画面と一致するかを見る。

## プロフィールの扱い方（Phase 2）

**既定は「隠す」ではなく「並べ替えと強調」。** 設計の「表示の原則」に合わせている。

| 場面 | 挙動 |
| --- | --- |
| プロフィール未設定 | すべての予定が見える。設定を促す案内だけ出す |
| 保存後（既定） | 該当するイベントに「対象」の印と枠の強調が付く。該当しないものも消さない |
| 「自分に関係するものだけ表示する」 | 該当するもの、全員向けのもの（`audience` が空）、MY予定だけを表示する |

- 該当理由は「あなたのグレード」「シーズンパス」の文字で示す。色だけに依存させない。
- `audience` に複数のキーがある場合は、いずれかを満たせば該当として扱う。
- 一般販売（`audience` が `{}`）は全員向けとして扱い、印は付けないが絞り込みでも残す。
- 時系列は崩さない。並べ替えは同時刻のイベントどうしの順序にだけ効かせる。
- 「次にやること」は、プロフィールがある場合、自分に該当するものと全員向けの中から直近の1件を選ぶ。
  他グレードの先行販売は一覧には残るが、行動を促す位置には出さない。

## 見せ方

実データを入れて分かったのは、情報が正しくても並べ方次第で読めなくなること。2026-08-28に次を入れた。

**量の問題は実データを全部入れて初めて見えた。** ホーム19試合ぶん149件を入れると、
これからの予定だけで77枚、日付見出しが67個、ページの高さが20,371px（幅430pxで約23画面分）になり、
日付の見出しがカードとほぼ1対1で、まとまりとして機能していなかった。

| 決めたこと | 理由 |
| --- | --- |
| 月で区切り、当月と翌月だけ開く | 実データは9か月先まである。全部開くと20,000pxを超えて読めない。**20,371px → 8,454px** になった |
| 畳んだ月には件数を出す（「2026年10月 16件」） | 中に何件あるか分からないと開く判断ができない |
| その日に1つの試合しかなければ、日付と試合名を1行にまとめる | 1日1試合ぶんの日がほとんどで、見出しが2行に分かれると場所を取るだけ |
| 「次にやること」を画面下のドロワーにする | ページ上部だとスクロールした瞬間に見えなくなる。閉じて1件、開いて5件 |
| 終わったものは「終わったもの ◯件を表示する」に畳む | 開いた瞬間に見えるのが過去だと、いま何をすべきか分からない。消さないのは後から確かめたいときがあるため |
| 同時刻の先行販売と特典チケット引換を1枚にまとめる | 同じ等級なら必ず同時刻。別カードだと1試合で8枚並び、同じ時刻が2回続く |
| 日付の下を試合名で区切る | 1本の時系列は崩さず、まとまりだけ付ける |
| 見出しで試合名を出したカードからは題とメタの試合名を省く | 「第7節 柏戦」の下に「柏戦 ゴールド先行販売」だと同じ語が3回出る |
| 種別をイラストで示す | 枠線だけでは何のアクションか分かりにくい。アイコンは `aria-hidden` の装飾で、文字ラベルは残す |
| 設定は未設定なら開き、設定済みなら畳む | 毎回使うのはタイムライン。設定は一度きり |

**アイコンは記号の置き換えではない。** `★` `◎` をやめたのは、文字として読み上げられて意味が伝わらないため。
アイコンは `aria-hidden` なので読み上げられず、文字ラベルがそのまま読まれる。

**「次にやること」は1件では足りなかった。** 直近1週間に複数の販売と締切が並ぶため、
1件だけだとその次を見るのにタイムラインを探すことになる。ドロワーを開くと直近5件が出て、
6件目以降は件数だけ伝える（「ほか35件はタイムラインで見られます」）。

### 配色（2026-08-28 作り直し）

本番移植に向けて、入口ページ（`public/assets/index.css`）を基準に作り直した。判断の経緯は
`docs/supporter-timeline-design.md` の「地は入口ページのネビュラ、内容は白場に載せる」を正とする。

| 決めたこと | 理由 |
| --- | --- |
| 地を入口ページのネビュラにする | 3つの公開ページで唯一 `--radius` `--tap` を持ち、`rem` とトークンで書かれている。年間スケジュールは `px` 固定で6pxの文字を持つため基準にしない |
| 背景は `public/assets/index-nebula.js` を直接読む | 同じ実装を確かめるため。WebGLが使えなければCSSのぼかしが残る（進行的強化） |
| 内容は白場（`.block`）に載せ、月と日付だけ地の上に出す | 札と札のあいだで背景が一定の間隔で見え、149件を白い面で受けられる |
| 白場の単位は「その日の・その試合ぶん」 | 「日付の下を試合で区切る」と同じまとまり。試合ブロックを `.block` で包んだ |
| 月見出しを紫（`#7b0064`）の帯にする | 細い罫線では地に沈んで、月の切れ目が読めなかった |
| 地の上の補助テキストを `rgba(255,255,255,0.86)` にする | 入口ページの `--ink-dim`（0.72）では、ネビュラ最明部（実測 `#a23c88`）に対して3.86で本文に不足。0.86で4.84 |
| `--muted` と `--link` を白い面で再定義する | 同じ変数を地と白場の両方で使うため。地では明るい白とシアン、白場では濃いグレーと `--accent` |
| 日程未定と取り込まなかった記事も白場に載せる | 内容だから。地の上では紫のリンクが背景と同化して読めなかった |

**コントラストはヘッドレスChromiumで全文字を実測した。** 地の上の文字はネビュラの最明部を
最悪ケースとして突き合わせ、基準（本文4.5:1）を満たさないものが無いことを確認している。

## 特典チケット

**公式に出るのは引換開始日時だけで、何枚持っていて、どの試合に引き換えるつもりかはどこにも残らない。**
シーズンが終われば価値が消えるため、計画を立てられないこと自体が損になる。

**「使う」ではなく「引き換える」。** 特典チケットは試合のチケットに引き換える方式で、入場したかどうかとは
別の行為。引き換えた時点で1枚が消費される。文言も保存する状態も「引き換える予定」「引き換えた」で統一する。

**枚数は1つの数ではなく、理由つきの増減で記録する。** 家族の分をまとめて持っていたり、
友人と譲り合ったりするため、「いま何枚か」だけでは自分の記録を信用できなくなる。合計は履歴から出す。

| 理由 | 符号 |
| --- | --- |
| 会員特典として受け取った | + |
| 譲り受けた | + |
| 譲った | − |
| 数え直して増やす / 減らす | + / − |

**譲渡は引き換えではないので、引き換えの記録とは別に持つ。** 「何枚を誰に渡したか」と
「何枚を試合に充てたか」を別々に追えるようにするため。メモは任意で30字まで、端末から出ない。

| 操作 | 結果 |
| --- | --- |
| 会員種別を保存する | 公式の配布枚数を「会員特典として受け取った」で記録するよう案内する（ゴールドなら3枚） |
| 増減を記録する | 合計が更新され、残り枚数と内訳（持っている / 引き換える予定 / 引き換えた）が出る |
| 試合と枚数を選んで「引き換える予定にする」 | 残りが減り、その試合のキックオフに「特典チケットを◯枚 引き換える予定」が付く |
| 同じ試合にもう一度足す | `count` を合算する。**1試合に複数枚まとめて引き換えられる** |
| 「引き換えた」 | 記録が「引き換えた」に変わる。予定に戻すことも、記録を消すこともできる |
| 増減の記録を消す | 1件ずつ取り消せる。合計が計算し直される |
| 残り枚数 > これからのホーム戦 | 「1試合に複数枚まとめて引き換えないと、使わないまま残ります」と警告 |

自分の等級の引換イベントには「特典チケットは残り◯枚」を添える。

### 配布枚数と利用条件

`benefit-tickets.json`（2026-08-28に公式で確認）から読む。

| コース | 特典チケット |
| --- | --- |
| プラチナクルー | 3枚（構成からの推定） |
| ゴールドクルー | 3枚（公式に明記） |
| レギュラークルー | 1枚（公式に明記） |
| キッズクルー | 1枚（公式に明記） |

有効期間「2026-27シーズンでのみ使用可能」と、利用条件「一部対象外の試合が設定される場合がある」
「対象席種が完売した場合は利用できない」を画面に併記する。残り枚数だけを見て引き換えられると
誤解させないため。**公式の表記をそのまま出し、こちらで暦日に言い換えない。**

### 印は記号ではなく言葉

`★` や `◎` は音声読み上げで意味が伝わらないため使わない。
「あなたのグレードが対象」「特典チケットは残り3枚」のように、読み上げてそのまま意味が通る文にする。
視覚的な区別は枠線と背景色で付ける。

### 自己申告であること

引換の実績を知る手段がないため、枚数も「引き換えた」も利用者が入力する。
日程未定・候補日のホーム戦も「これから引き換えられる試合」に数える。日程が決まっていないだけで、
引き換えられる機会だから。個々の試合が対象かどうか（対象外試合・席種の完売）は判定しない。

### Phase 2（ヘッドレスChromium・幅430px・2026-08-28）

実データ（5試合分）で確認した結果。

| 確認したこと | 結果 |
| --- | --- |
| 未設定時 | 印なし。「自分に関係するものだけ表示する」は無効。タイムラインに40件が並ぶ |
| ゴールドクルーを保存 | ゴールド先行販売と特典チケット引換の計8件に「あなたのグレードが対象」。件数は40件のまま変わらない |
| シーズンパスも有効にする | シーズンパス先行受付にも「シーズンパスが対象」が付く |
| 「自分に関係するものだけ表示する」 | 40件→20件。他グレードの先行販売と引換が外れ、一般販売と全員向けは残る |
| 「次にやること」 | 「あなたのグレードが対象です」を添えてゴールドクルー先行を表示 |
| 再読み込み | 保存した設定と印が復元される |
| 「保存した設定を削除する」 | LocalStorageのキーが消え、未設定の表示に戻る。MY予定は残る |

## MY予定とICS

**現在、MY予定もICSに含まれる。** 端末内で生成するファイルなので、個人の予定が外部へ出ることはない。
「座席へ移動」のような予定をカレンダーに入れられるのは、設計の狙いどおり。

一方で、実機確認では「トイレ」というMY予定がそのまま書き出された。
**カレンダーに残したくない種類の予定もある**ため、次のどちらにするかは要検討。

ただしiOSでは取り込み前のプレビューで個別に外せる見込みがあり、実害は小さいかもしれない。
Androidにはこの画面がないため、扱いが分かれる。

| 案 | 内容 |
| --- | --- |
| 現状のまま | 絞り込みで制御する。表示中のものだけが書き出される |
| 選べるようにする | 「MY予定を含める」のチェックを付ける |
