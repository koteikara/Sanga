# SUPPORTER TIMELINE（Phase 1・Phase 2 プロトタイプ）

作成日: 2026-08-27（Phase 2 追加: 2026-08-28）

## 目的

`docs/supporter-timeline-design.md` の Phase 1 と Phase 2 を、移植前に見た目と操作感で確認する。
設計文書だけでは決まらない次の5点を、実際に触って確かめるためのもの。

| 確認したいこと | 見るところ |
| --- | --- |
| 「次にやること」と全体タイムラインを分けたときの見え方 | 画面上部と中段 |
| `date_precision` による出し分け | タイムラインと「日程未定」 |
| MY予定が公式イベントと同じ時系列に並ぶか | MY予定を追加してからタイムライン |
| 確定した日時だけがICSへ出ること | 「カレンダーへ書き出す」 |
| プロフィールで自分の先行販売が分かるか | 「あなたの設定」を保存してからタイムライン |
| 実データの件数でタイムラインが破綻しないか | 5試合分・全43件のタイムライン |
| 特典チケットの残り枚数と使い道が管理できるか | 「特典チケット」の枚数入力と割り当て |

## 今回やったこと

- TimelineEventスキーマの形をサンプルJSONで表現した
- 「次にやること」（直近のACTION 1件）と全体タイムラインを分けた
- 種別の絞り込み（すべて / チケット / 応募 / 試合当日 / MY予定）
- `date_precision` の4値を出し分けた
- MY予定の追加・削除（LocalStorage）
- ICS書き出し（日時が確定しているものだけ）
- 取り込まなかった記事の一覧表示

### Phase 2（2026-08-28 追加）

- プロフィール入力UI（SANGA CREW 会員種別、シーズンパスの有無）
- プロフィールの保存・削除（LocalStorage `sanga-timeline-profile-v1`）
- `audience` との照合。該当するイベントに★バッジ（「あなたのグレード」「シーズンパス」）を付ける
- 「次にやること」を、自分に該当するものと全員向けだけから選ぶ
- 「自分に関係するものだけ表示する」の任意の絞り込み
- 特典チケットの管理（枚数の自己申告、試合への割り当て、使った記録、残り枚数と残りホーム戦の突き合わせ）

- プロフィールの書き出し・読み込み（端末を変えると消える）
- 変更検知

- 通知、PWA

## データ

| ファイル | 内容 |
| --- | --- |
| `calendar-events.sample.json` | チケット販売は実データ、試合当日のイベント等は作り物。`events` と `skipped` を持つ |
| `matches.sample.json` | `public/data/matches.json` からの抜粋。正本ではない |

**チケット販売の33件は実データです。** `docs/sheets/ticket-sales.2026-08-28.csv`（公式のチケット販売
スケジュールを2026-08-28に確認したスナップショット）から作りました。対象は第4節 福岡、第7節 柏、
第9節 町田、第21節 横浜FM（開催日は候補のまま）、第20節 岡山（販売日程が未告知）の5試合です。

**それ以外のイベントは検証用の作り物です。** 開門、Tシャツ配布、エスコートキッズ応募、
ACLユニフォーム販売、アウェイ交流ブースには `"is_sample": true` を付けています。日時もURLも実在しません。

1試合の販売は**先行販売5段階と特典チケット引換3件の、合わせて8件**です。

| 段階 | 時刻 | `audience` |
| --- | --- | --- |
| シーズンパス先行受付 | 11:00 | `{"season_ticket": true}` |
| プラチナ先行販売 / 特典チケット引換 | 12:00 | `{"fc_grade": ["platinum"]}` |
| ゴールド先行販売 / 特典チケット引換 | 12:00 | `{"fc_grade": ["gold"]}` |
| レギュラー・キッズ先行販売 / 特典チケット引換 | 12:00 | `{"fc_grade": ["regular","kids"]}` |
| 一般販売 | 12:00 | `{}` |

**同じ試合の販売が8件並ぶ様子を見るためのもの。** 自分に関係するのは1〜3件で、残りは見なくてよい。
プロフィールによる強調（Phase 2）が要る理由がここにある。ゴールドクルーを設定すると、
タイムラインの40件が「自分に関係するものだけ表示する」で20件になる。
既定では40件すべてが並んだままで、★が付くだけ。

実データで分かったことは `docs/supporter-timeline-design.md` の「販売段階は8つある」を正とする。

**販売日時は時間が経つと過去になる。** 「次にやること」が空になった場合は、
より先の試合をCSVから足すか、スナップショットを取り直す。

`skipped` は「取り込まなかった記事」を表す。設計上、機械的に確実に読めなかった記事は日時を抽出せず、
URLだけ残す。理由コードは `image_only` / `revision_history` / `multiple_events` / `no_label` / `date_inherited` の5つ。
現在の5件は作り物のサンプル。

## LocalStorage

| キー | 保存形式 | 用途 |
| --- | --- | --- |
| `sanga-timeline-personal-events-v1` | TimelineEventの配列 | MY予定 |
| `sanga-timeline-profile-v1` | `{ fc_grade, has_season_ticket, updated_at }` | サポータープロフィール |
| `sanga-timeline-benefit-tickets-v1` | `{ total, uses: [{ match_id, status, updated_at }], updated_at }` | 特典チケットの枚数と使い道 |

プロフィールは端末内だけで扱う。照合もサーバーへ送らずに画面側で行うため、個人の属性はどこにも記録されない。
`fc_grade` は `platinum` / `gold` / `regular` / `kids` / `none` と未設定（空文字）のみを保存し、
知らない値が入っていた場合は未設定として扱う。「保存した設定を削除する」で消せるのはプロフィールだけで、MY予定は消さない。

**既存の `sanga-schedule-*` キーには触れない。** 年間スケジュールページの状態を壊さないため。
公開JSONにも個人の予定は含めない。

## ICSについて

書き出すのは `date_precision` が `datetime` または `date` のものだけ。
`candidates`（候補日が複数）と `unknown`（日程未定）は含めない。

購読カレンダーに入った予定は利用者にとって確定情報として届くため、候補日を流すと誤情報になる。
確定した時点でフィードに現れるほうが信用できる、という判断による。

書き出したファイルは `sanga-timeline-sample.ics`。カレンダーアプリで開いて、
日時と件数が画面と一致するかを見る。

## プロフィールの扱い方（Phase 2）

**既定は「隠す」ではなく「並べ替えと強調」。** 設計の「表示の原則」に合わせている。

| 場面 | 挙動 |
| --- | --- |
| プロフィール未設定 | すべての予定が見える。設定を促す案内だけ出す |
| 保存後（既定） | 該当するイベントに★バッジと枠の強調が付く。該当しないものも消さない |
| 「自分に関係するものだけ表示する」 | 該当するもの、全員向けのもの（`audience` が空）、MY予定だけを表示する |

- 該当理由は「あなたのグレード」「シーズンパス」の文字で示す。色だけに依存させない。
- `audience` に複数のキーがある場合は、いずれかを満たせば該当として扱う。
- 一般販売（`audience` が `{}`）は全員向けとして扱い、★は付けないが絞り込みでも残す。
- 時系列は崩さない。並べ替えは同時刻のイベントどうしの順序にだけ効かせる。
- 「次にやること」は、プロフィールがある場合、自分に該当するものと全員向けの中から直近の1件を選ぶ。
  他グレードの先行販売は一覧には残るが、行動を促す位置には出さない。

## 特典チケット

**公式に出るのは引換開始日時だけで、何枚持っていて、どの試合に使うつもりかはどこにも残らない。**
シーズンが終われば価値が消えるため、計画を立てられないこと自体が損になる。

タイムラインは試合日程を持っているので、残り枚数と「これから使えるホーム戦」を突き合わせられる。

| 操作 | 結果 |
| --- | --- |
| 持っている枚数を入れる | 残り枚数と内訳（持っている / 使う予定 / 使った）が出る |
| 試合を選んで「使う予定にする」 | 残りが1枚減り、その試合のキックオフに「特典チケットを使う予定」が付く |
| 「使ったことにする」 | 記録が「使った」に変わる。取り消して予定に戻せる |
| 残り枚数 > 使い道を決めていないホーム戦 | 「使い切れないおそれ」を警告として出す |

自分の等級の引換イベントには「特典チケット 残り◯枚」を添える。

**すべて自己申告。** 引換や入場の実績を知る手段がないため、枚数も「使った」も利用者が入力する。
日程未定・候補日のホーム戦も「これから使える試合」に数える。日程が決まっていないだけで、使える機会だから。

等級ごとの配布枚数と有効期限は未確認のため、枚数の初期値は出さない。
1試合に複数枚使う場合（同伴者分など）は扱っていない。

### Android（実機・2026-08-27）

| 確認したこと | 結果 |
| --- | --- |
| `.ics` のダウンロード | 成功。2.98 KB のファイルとして保存された |
| カレンダーアプリへの受け渡し | **成功。** 「アプリで開く」からカレンダー、Outlook等を選べる |

**ICSをPhase 1に含める判断は、Androidでは成立している。** ダウンロードした`.ics`を
カレンダーアプリが受け取れるため、通知をカレンダー側に任せられる。

ただしこれは**その時点の予定を1回取り込む**動作であり、購読フィードのような自動同期ではない。
日時が変わったときに追随するには、静的な購読フィード（`webcal:`）が要る。

### iPhone Safari（実機・2026-08-27）

| 確認したこと | 結果 |
| --- | --- |
| `.ics` のダウンロード | 成功 |
| カレンダーアプリへの受け渡し | **成功。しかもAndroidより丁寧。** 取り込み前にプレビューが出る |

**iOSは取り込み前に確認画面を出す。** 「9件の予定」という件数と全件のリストが表示され、
「すべて追加」で一括登録できる。左上のチェックから個別に選ぶこともできる見込み。

表示された内容はプロトタイプ画面と一致した。

| 項目 | 結果 |
| --- | --- |
| 件数 | 9件（画面の表示と一致） |
| 日時 | 8/28 12:00、8/29 12:00 / 17:00 / 19:00、9/1 23:59、9/3 19:00 すべて正しい |
| 終了時刻 | Tシャツ配布が `17:00 - 19:00` と表示され、`DTEND` が効いている |

**同時刻イベントの並び順は制御できない。** 8/29 の17:00で、プロトタイプ画面では

カレンダーアプリ側の並べ方によるもので、実害はないが、順序を前提にした設計はできない。

**ICSをPhase 1に含める判断は、AndroidとiOSの両方で成立した。**

## MY予定とICS

**現在、MY予定もICSに含まれる。** 端末内で生成するファイルなので、個人の予定が外部へ出ることはない。
「座席へ移動」のような予定をカレンダーに入れられるのは、設計の狙いどおり。

一方で、実機確認では「トイレ」というMY予定がそのまま書き出された。
**カレンダーに残したくない種類の予定もある**ため、次のどちらにするかは要検討。

ただしiOSでは取り込み前のプレビューで個別に外せる見込みがあり、実害は小さいかもしれない。
Androidにはこの画面がないため、扱いが分かれる。

| 案 | 内容 |
| --- | --- |
| 現状のまま | 絞り込みで制御する。表示中のものだけが書き出される |
| 選べるようにする | 「MY予定を含める」のチェックを付ける |

## 分かっていないこと

- iOS Safari で `.ics` のダウンロードがどう扱われるか。購読フィード（`webcal:`）との差も未確認
- 実データの件数が増えたときのタイムラインの長さと、初期スクロール位置
- 過去のイベントの扱い（現状は時系列にそのまま残る）
- 端末を変えたときのプロフィールの引き継ぎ（書き出し・読み込みは未実装）
- 等級ごとの特典チケットの配布枚数と有効期限。枚数は利用者の自己申告のまま
- 1試合に複数枚使う場合（同伴者分など）の扱い
- 同時刻に並ぶ「先行販売」と「特典チケット引換」のどちらを「次にやること」に出すべきか。
  現在は同時刻の順序を制御していないため、引換が先に出ることがある
- リーグ戦以外（カップ戦・ACL）の販売段階の構成
